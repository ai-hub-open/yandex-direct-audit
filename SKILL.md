# Yandex Direct — аудит и точки роста

Скилл проводит маркетолога через **диагностику работающего аккаунта** Яндекс.Директа: от инвентаризации до приоритизированного списка находок «срезать слив / масштабировать / починить». Фокус — только **анализ существующих кампаний**. Создание новых кампаний с нуля и автоматическое внесение правок — **не задача этого скилла**.

Скилл опирается на два источника, и в этом его сила: **Direct MCP** (`yandex-direct`, JSON API v5/v501) для расходов/кликов/структуры и **Яндекс.Метрику** через `scripts/metrika_api.py` (read-only, OAuth-токен) для поведения и правды про конверсии. Direct отвечает «сколько потрачено и сколько кликов», Метрика — «что эти люди делали на сайте и где правда про конверсии». Связка идёт через Direct-срезы Метрики (`ym:s:<attribution>DirectClickOrderName` = кампания, `...DirectPlatform` = площадка, `...DirectPhraseOrCond` = условие показа), поэтому поведенческие данные ложатся ровно на сущности Директа. Подробности доступа — `references/mcp-tools-map.md` и `references/metrika-integration.md`.

## Когда триггерится

- «Проанализируй кампанию / аккаунт» / «сделай аудит Директа»
- «Почему сливается бюджет» / «где теряем деньги» / «куда уходят деньги»
- «Найди точки роста» / «что можно улучшить»
- «Что не так с рекламой / с кампанией»
- «Дай рекомендации по оптимизации» / «как поднять конверсии»
- «Проверь поисковые запросы / минусы / площадки / корректировки»

## Главный принцип: только чтение, решение — за человеком

Скилл работает в режиме **read-only** и вызывает только `*_get`, `report_*`, `dictionaries_*` и `api_call` исключительно для отчётов. Пишущие тулы (`*_add`, `*_update`, `*_delete`, `*_suspend`, `*_resume`, `*_moderate`, `bidmodifiers_demographics`) он не трогает.

Причина не в формальном запрете, а в природе задачи: вывод «отключить площадку» или «списать запрос в минус» на основе 30 дней может быть ошибкой в сезонной или низкочастотной нише, где данных мало, а сегодняшний ноль конверсий завтра станет продажей. Поэтому каждое предлагаемое изменение — это **строка-рекомендация в отчёте** с доказательством и порогом, а нажимает кнопку маркетолог. Это и есть человеческий чек-пойнт, ради которого скилл существует. Если по ходу анализа возникает соблазн «просто внести правку» — это сигнал оформить её как рекомендацию, а не как действие.

**Каждый шаг порождает артефакт.** Рабочая папка: `direct-audits/<slug>/`. Артефакты накапливаются и служат входами для следующих шагов и финального отчёта.

**Каждый флаг несёт доказательство, порог и контекст объёма.** Вывод на трёх кликах бесполезен и вреден: если данных мало, честнее написать «недостаточно данных», чем выдать ложную уверенность.

## Как использовать scripts

- `scripts/normalize_report.py` — парсит TSV-ответ отчёта Директа → нормализованная таблица (деньги из микро в рубли, расчёт CPA/ДРР/CR), фильтрация до строк, нарушающих пороги или несущих существенный расход, ранжирование по расходу. Вход — сырой TSV отчёта, выход — JSON + краткий ranked-срез для рассуждения.
- `scripts/metrika_api.py` — read-only доступ к Яндекс.Метрике (Reporting API + список целей) через OAuth-токен в окружении. Пресеты `goals / attribution / placements / queries / segments` тянут поведение и конверсии и кладут их на сущности Директа через Direct-срезы. `--dry-run` показывает запрос без вызова API. См. `references/metrika-integration.md`.
- `scripts/render_report.py` — собирает финальный **PDF-отчёт** (стиль «дашборд») из `findings.json`: строит HTML с оформлением и печатает его в PDF уже установленным Chrome/Edge (headless). Внешних pip-пакетов не требует. `--input <findings.json>` обязателен; `--output <pdf>` и `--open` — опционально. Используется на Шаге 7. См. `references/report-template.md`.

# Workflow: 7 шагов

## Шаг 0. Скоуп аудита

**Прочти `references/mcp-tools-map.md` целиком.** Без Direct MCP live-аудит невозможен — стоп. Токен Метрики скрипт берёт из окружения **или из `.env`** в корне проекта (`YANDEX_METRIKA_TOKEN`, либо общий `YANDEX_DIRECT_TOKEN` со скоупом `metrika:read`); нет токена → аудит идёт по Директу в урезанном режиме (без поведения и правды про конверсии) — честно предупреди.

### Предполётная проверка доступов (read-only, до сбора скоупа)

Прежде чем задавать вопросы и жечь квоту — подтверди, что каждый канал доступа реально **работает**, а не просто «настроен». Все вызовы read-only.

1. **Директ живой.** `campaigns_get({ limit: 1 })`. Отвечает и не пусто → MCP, авторизация и логин в порядке. Ошибка/`isError` → проблема авторизации; пусто → не тот `Client-Login`, уточни. Нет тула → MCP не подключён, стоп.
2. **Метрика живая + доступ к счётчику.** Как только известен `counter_id` (из скоупа ниже или из `CounterIds` на Шаге 1) — `python -m scripts.metrika_api --counter <id> --preset goals`. Вернулись цели → токен валиден, скоуп `metrika:read` есть, доступ к счётчику есть (список целей всё равно нужен на Шаге 1 — вызов не впустую). HTTP 403 → токен не видит этот счётчик; 401 → токен протух/неверен: продолжай в режиме «без Метрики» и предупреди маркетолога.
3. **Отчёты Директа.** Отдельным вызовом эндпоинт `/json/v5/reports` НЕ проверяй (не занимай слот очереди офлайн-отчётов) — проверка повешена на **первый реальный отчёт Шага 2**: упал с ошибкой эндпоинта → зафиксируй ограничение там же (см. `mcp-tools-map.md`).
4. **Сверка счётчика.** После Шага 1 сверь счётчик из `CounterIds` кампаний с тем, что реально открыл токен (п. 2). Расходятся → предупреди: поведенческие срезы Метрики могут не сойтись с кампаниями.

Любой красный пункт → скажи маркетологу **до старта**, какой доступ не работает и как это сузит аудит. Не падай на середине и не выдавай тихо пустые данные. Результаты запиши в `_state.json` (`mcp_ok`, `metrika_ok`, `reports_ok`, `counter_match`).

Задай маркетологу **одним блоком** скоуп:
1. **Клиент / логин** — если MCP мультиаккаунтный (`Client-Login`), какой аккаунт анализируем.
2. **Период** — по умолчанию `LAST_30_DAYS`; для трендов добавим предыдущие 30 дней. Сезонным нишам — уточнить.
3. **KPI** — целевой CPA и/или ДРР (drr = расход ÷ выручка), целевой CPL. Если KPI нет — аудит будет по относительным сигналам (слив, аномалии), но без вердикта «дорого/дёшево».
4. **Фокус** — весь аккаунт или конкретные кампании? Что болит (бюджет / конверсии / конкретная кампания)?
5. **Счётчик и цели Метрики** — `counter_id` (если не знает — возьмём из `CounterIds` кампаний на Шаге 1) и какие `goal_id` считать конверсиями (иначе вытащим список целей пресетом `goals`).
6. **slug** — короткое имя проекта для рабочей папки.

**Модель атрибуции** в скоупе не спрашивай — её определяем **отдельно для каждой кампании** из её настроек на Шаге 1 (правило: берём модель кампании, если не задана — `LSCCD`/последний значимый переход с кросс-девайсом). Единый словарь Direct↔Метрика и правило — в `references/metrika-integration.md`.

**Артефакт:** `direct-audits/<slug>/00_scope.md` + `_state.json` (current_step, slug, client_login, period, kpi_cpa, kpi_drr, counter_id, goal_ids, attribution_default, metrika_available, focus, mcp_ok, metrika_ok, reports_ok, counter_match). Поле `attribution_default` — запасная модель, если кампания свою не отдаёт (по умолчанию `LSCCD`); фактические модели по каждой кампании заполняются на Шаге 1.

Гипотеза вместо допроса: если что-то не сказано — предложи дефолт («Беру последние 30 дней и весь аккаунт, KPI пока нет — согласен?»).

## Шаг 1. Инвентаризация и структурный аудит

**Прочти раздел «Структура аккаунта» в `references/audit-thresholds.md`.**

```
yandex_direct_campaigns_get({ limit: 10000 })
```

`limit: 10000` — максимум, который Директ отдаёт за один ответ; этого хватает на любой реальный аккаунт. Если в ответе пришёл `LimitedBy` со значением 10000 (кампаний реально больше) — дозабери остаток постранично через `offset`, пока не выберешь все. Цель шага — **полная** опись, частичная карта ломает все следующие шаги.

Для каждой кампании зафиксируй: `Id`, `Name`, `Type` (TEXT_CAMPAIGN / UNIFIED_CAMPAIGN / др.), `State`/`Status`, `Strategy` (Search + Network: тип, цель, лимиты), `DailyBudget`, привязка счётчика Метрики, **модель атрибуции** (отдельно для каждой кампании, из настроек конверсий/Метрики кампании; точное имя поля сверь с рантаймом MCP — в обёртках различается; нет поля → `LSCCD`), `NegativeKeywords`, `ExcludedSites` (если отдаёт). При необходимости — `adgroups_get` для понимания вложенности.

**Структурные проверки (это уже находки):**
- Поиск и РСЯ — раздельными кампаниями? Смешано → флаг.
- ЕПК (`UNIFIED_CAMPAIGN`) — детектить и анализировать как смешанное размещение (Поиск + Сеть + товарные); часть срезов по ней беднее, см. оговорки в reference.
- Счётчик Метрики привязан? Цели есть? Нет → поведенческие/конверсионные метрики будут пустыми, отметить как блокер аналитики.
- Стратегия: авто vs ручная, цель оптимизации, дневные/недельные лимиты — адекватны?
- Корректировки ставок вообще заданы? (полная проверка — Шаг 5)

**Артефакт:** `01_account_map.md` (таблица кампаний + структурные флаги) + `01_account_map.json` (machine-readable: список кампаний с типами, счётчиками, стратегиями, **моделью атрибуции** — вход для всех следующих шагов). Зафиксируй карту «кампания → CounterIds» и «кампания → модель атрибуции» — они нужны для всех вызовов Метрики. Если `counter_id` не был задан в скоупе — возьми его отсюда; если у кампаний разные счётчики, Метрику гоняем по каждому.

**Модель атрибуции (мост к Метрике).** Зафиксируй модель **отдельно по каждой кампании** (нет в настройках → `LSCCD`). Эту же модель применяй в Метрике на Шагах 2-5 — через единый словарь Direct↔Метрика (`metrika_api.py --attribution <Direct-код>` принимает коды кампаний напрямую). Раз модели по кампаниям могут различаться — **сгруппируй кампании по модели** и гоняй конверсионные пресеты Метрики по разу на группу (параметр `attribution` применяется ко всем строкам запроса сразу). Правило и таблица соответствия — `references/metrika-integration.md`.

**Бюджет квот:** `campaigns_get` дешёвый. Справочники (`dictionaries_regions` ~3 МБ) — только при необходимости, кэшируй в `_regions_cache.json`, грепай по имени (рецепт — `custom-report-recipes.md`, Рецепт 6).

### Метрика на этом шаге

Если цели не заданы — вытяни список целей счётчика: `python -m scripts.metrika_api --counter <id> --preset goals`. Сохрани в `_metrika_goals.json`, согласуй с маркетологом, какие считать конверсиями. Эти `goal_id` идут во все конверсионные запросы дальше.

## Шаг 2. Статистика по кампаниям

**Прочти раздел «Прибыльность и тренды» в `references/audit-thresholds.md` и `references/metrika-integration.md` (мост и атрибуция).**

По всем активным кампаниям из `01_account_map.json`:

```
yandex_direct_report_campaign({ campaign_ids: [...], date_range: "LAST_30_DAYS" })
```

Запрашивай метрики: `Impressions, Clicks, Ctr, Cost, AvgCpc, Conversions, ConversionRate, CostPerConversion, Revenue, BounceRate, AvgPageviews` + срез `AdNetworkType` (разделить Поиск/Сеть). При наличии целей — передавай `Goals` и фиксированную модель атрибуции (политику атрибуции зафиксируй в отчёте и указывай рядом с каждым числом).

⚠️ **Перед нормализацией — проверь формат денег (одна сверка, влияет на все шаги 2-5).** `normalize_report.py` по умолчанию считает суммы микро-валютой и делит на 1 000 000. Но MCP-обёртки часто уже отдают рубли — тогда деление лишнее и весь отчёт уедет в миллион раз. Посмотри одно поле `Cost` в сыром TSV: число вида `12400` — это уже рубли, добавь флаг `--money-in-rub`; число вида `12400000000` — это микро, оставь дефолт. Если сомневаешься — сверь `Cost` любой строки с тем, что видно в интерфейсе Директа. Тот же выбор флага применяй ко всем последующим прогонам скрипта (Шаги 3-5).

Прогони сырой TSV через `python -m scripts.normalize_report --input <raw.tsv> --kpi-cpa <X> --kpi-drr <Y>` (добавь `--money-in-rub`, если деньги уже в рублях) → получишь нормализованную таблицу с CPA/ДРР/CR и флагами.

### Метрика на этом шаге: атрибуционный кросс-чек (делает выводы точными)

Это ключ к точности. Прогони по кампаниям конверсии из Метрики и сравни модели:
```
python -m scripts.metrika_api --counter <id> --preset attribution --goal <id> --attribution lastsign
python -m scripts.metrika_api --counter <id> --preset attribution --goal <id> --attribution last_direct
```
Джойни по имени кампании (`DirectClickOrderName` ↔ Name из Директа). **Что ищем:** кампании, которые по Direct/последнему клику выглядят убыточными, но по `first`/ассоциированным конверсиям сидят вверху воронки — их НЕЛЬЗЯ резать, это была бы дорогая ошибка. Расхождение Direct vs Метрика — норма (разные модели), объясняй его моделью, а не «своди копейка в копейку».

**Что ищем (итого):** кампании выше/ниже KPI по CPA/ДРР; концентрацию бюджета; Поиск vs РСЯ; верх-воронки кампании, которые нельзя трогать. Тренд — повтори за предыдущий период равной длины.

**Артефакт:** `02_campaign_performance.md` + `02_campaign_performance.json` (включая колонки конверсий по двум моделям атрибуции).

**[GATE: маркетолог]** Покажи 5-10 строк сводки: «Вот картина по кампаниям. Копаем глубже в <худшие по CPA>?»

## Шаг 3. Майнинг поисковых запросов (минусация)

**Прочти раздел «Поисковые запросы → минусация» (внутри «Поиск слива бюджета») в `references/audit-thresholds.md`.**

По всем кампаниям с поисковым трафиком (Поиск + поисковая часть ЕПК):

```
yandex_direct_report_search_queries({ campaign_ids: [...], date_range: "LAST_30_DAYS" })
```

Нормализуй через скрипт. **Кандидаты в минус-слова** — запросы с расходом, но без конверсий и/или с высоким отказом. ⚠️ **Не предлагай минусовать** запросы с малым числом переходов (<5) — это шум, можно переограничить охват (см. предупреждение eLama в reference). Сгруппируй кандидаты по повторяющимся словам/темам (нерелевантные намерения, «бесплатно», «своими руками», конкуренты-нецелевые и т.п.).

### Метрика на этом шаге: поведение запросов

`python -m scripts.metrika_api --counter <id> --preset queries --goal <id>` даёт отказ/глубину/время по условиям-фразам Директа. **Это спасает от ложной минусовки:** запрос с расходом и нулём конверсий, но низким отказом и хорошей глубиной — НЕ в минус (конвертит с задержкой / нужна доработка посадочной), а запрос с высоким отказом — уверенный кандидат. Клади поведение рядом с расходом в каждую рекомендацию.

Формулировку фикса (минус-слово vs уточнение оператором, уровни минусовки, кросс-минусовка) бери из раздела «ПОИСК → Минусовка» в `optimization-playbook.md`.

**Артефакт:** `03_negative_candidates.md` (сгруппированные кандидаты с расходом, отказом и причиной) + `03_negative_candidates.json`. Это **рекомендации**, не правки.

## Шаг 4. Чистка площадок РСЯ

**Прочти раздел «Площадки РСЯ» (внутри «Поиск слива бюджета») в `references/audit-thresholds.md` и `references/custom-report-recipes.md` (рецепт площадок).**

По кампаниям с сетевым размещением нужен срез по `Placement`. В дедикейтед тулах его нет → собираем CUSTOM_REPORT через `yandex_direct_api_call` к эндпоинту отчётов (точный JSON — в reference). Поля: `Placement, AdNetworkType, Impressions, Clicks, Ctr, Cost, Conversions, BounceRate`, фильтр `AdNetworkType = AD_NETWORK`.

⚠️ Если `api_call` в твоём MCP **не достаёт** до `/json/v5/reports` (проксирует только обычные сервисы) — зафиксируй это как ограничение, собери что можешь из `report_campaign` со срезом сети, и порекомендуй расширить reports-тул MCP. Не выдумывай данные по площадкам.

**Что ищем:** площадки с высоким расходом + ноль конверсий → кандидаты в `ExcludedSites`; аномально высокий CTR в сети (≥2%, см. порог eLama в reference) → подозрение на «клик под кнопкой» / фрод.

### Метрика на этом шаге: поведение по площадкам (надёжная чистка)

Раньше это было слепой зоной — теперь нет. `python -m scripts.metrika_api --counter <id> --preset placements --goal <id>` даёт отказ/глубину/время по каждой площадке Директа (аналог отчёта «Директ, площадки»). Джойни по имени площадки (`DirectPlatform` ↔ `Placement`). Чистка становится доказательной: «площадка X — расход 12 400 ₽, 0 конверсий (Direct) + отказы 81%, 9 сек на сайте (Метрика) → отключить, уверенность высокая» против «расход есть, конверсий нет, но отказы 25% и глубина 3 — подождать, не резать». Клади обе стороны в каждую рекомендацию.

Порог отключения (множители ×CPA) и приоритет (DSP → мобильные игры → нулевые после 100+ кликов) — из раздела «РСЯ → Чистка площадок» в `optimization-playbook.md`.

**Артефакт:** `04_placement_candidates.md` (площадки на отключение + расход + поведение + причина) + `04_placement_candidates.json`. Рекомендации.

## Шаг 5. Корректировки ставок (точки роста)

**Прочти раздел «Корректировки ставок» в `references/audit-thresholds.md` и `references/custom-report-recipes.md` (рецепты сегментации).**

Текущие корректировки:
```
yandex_direct_bidmodifiers_get({ campaign_ids: [...] })
```

Срезы эффективности (CUSTOM_REPORT через `api_call`, рецепты в reference): по `Device`, по `Gender`+`Age`, по `LocationOfPresenceName` (гео), по часу суток. Метрики: `Cost, Clicks, Conversions, CostPerConversion, ConversionRate`. Для гео-рекомендации может понадобиться расшифровка имени региона в `region_id` (корректировки ставятся по id) — справочник `dictionaries_regions`, Рецепт 6 в `custom-report-recipes.md`.

**Что ищем:** сегмент много тратит и плохо конвертит (CPA выше KPI / ноль конверсий при заметном расходе) → рекомендация отрицательной корректировки; сегмент перевыполняет → положительная. Полное отсутствие корректировок при явной разнице сегментов → флаг «аккаунт не настроен». ⚠️ Сегмент с <~10 конверсий за период — данных мало, помечай как «гипотеза, нужно накопить».

### Метрика на этом шаге: поведение сегментов на сайте

`python -m scripts.metrika_api --counter <id> --preset segments --segment device|gender|age|geo --goal <id>` даёт отказ/глубину/реальные цели по сегменту на уровне сайта (только Direct-трафик). Это усиливает рекомендацию: «мобайл — 68% расхода, CPA 2 300 ₽ (Direct) + отказы 70% против 35% на десктопе (Метрика) → корректировка MOBILE −20% обоснована поведением, а не только ценой клика». Поведение из Метрики делает гипотезу по % увереннее.

Формулу расчёта корректировки (последовательное умножение, диапазоны, приоритет, поведение в конверсионных стратегиях) бери из раздела «ОБЩЕЕ → Корректировки ставок» в `optimization-playbook.md`.

**Артефакт:** `05_bid_modifier_opportunities.md` + `05_bid_modifier_opportunities.json`. Рекомендации с конкретными % (как гипотеза, подкреплённая поведением).

## Шаг 6. Объявления и релевантность

**Прочти раздел «Креативы и релевантность» в `references/audit-thresholds.md`.**

```
yandex_direct_report_ad({ campaign_ids: [...], date_range: "LAST_30_DAYS" })
```

**Что ищем:** низкий CTR на Поиске (<2% → флаг релевантности/расширений); группы с одним объявлением (нет теста); сравнение вариантов внутри группы — победителя выбираем **по конверсиям/CPA, а не по CTR** (объявление с меньшим CTR, но большим числом конверсий лучше). При желании — проверка кросс-минусовки (объявления конкурируют в одном аукционе) по пересечению ключей из `keywords_get`.

Конкретные рычаги (ключ в Заголовок 1, расширения, кластеры вместо SKAG, комбинаторные креативы в РСЯ, правила A/B) — из разделов «ПОИСК → CTR/Структура», «РСЯ → Креативы» и «ОБЩЕЕ → A/B-тесты» в `optimization-playbook.md`. Помни: победитель A/B — по конверсиям/CPA, не по CTR.

**Артефакт:** `06_creative_findings.md` + `06_creative_findings.json`. Рекомендации.

## Шаг 7. Сборка отчёта (PDF)

**Прочти `references/report-template.md` целиком.**

Собери все находки Шагов 1-6 в единый `findings.json` (схема — в reference; заполненный образец на 5 находок и 3 кампании — `assets/findings_schema_example.json`, бери его за шаблон). Затем **собери из него PDF** скриптом:

```
python -m scripts.render_report --input direct-audits/<slug>/findings.json
# → АУДИТ_<slug>.pdf рядом (+ .html-исходник). --open чтобы открыть.
```

PDF — это и есть финальный отчёт для маркетолога (стиль «дашборд»). Скрипт сам находит Chrome/Edge и печатает в PDF, pip-пакетов не требует. Браузер не найден → `.html` сохраняется рядом, маркетолог печатает сам (Ctrl+P → Сохранить как PDF) — сообщи об этом.

**Заполни схему так, чтобы собрался дашборд:**
- `meta.summary` — 4 плашки: `total_cost`, `avg_cpa`, `recoverable` (потенциал экономии = деньги, уходящие впустую, ≈ сумма `money_impact` срочных находок слива), `growth_potential` (оценка роста).
- `meta.campaigns` — шкала расхода + KPI по каждой кампании (`cpa`, `drr`, `kpi_status`).
- Каждая находка несёт `campaign` (для группировки), `area` (человеческим именем), `severity`, `money_impact` (для топа), `recommendation`, `where` (где в Директе), `ready_to_use` (готовый список или null), `evidence`, `threshold`, `how_to_verify` (как перепроверить самому), `expected_effect`, `confidence`, `volume_note`.

**Структура PDF** (детали — в reference): дашборд + «Главное» (топ-5 по деньгам) → «Что сделать в каждой кампании» (разделы по кампаниям с карточками-действиями) → «Чего не смогли проверить». Внутри кампании карточки по убыванию важности.

**Приоритизация** следует порядку влияния из `optimization-playbook.md` (раздел «Приоритизация исправлений»): сначала фундамент (разделить Поиск/РСЯ, цели Метрики) и быстрый возврат денег (доп. релевантные фразы, «Мало показов», чистка площадок), затем минусовка, корректировки, креативы, и в конце A/B и тонкая настройка автостратегий.

**Язык отчёта:** человеческий, без техжаргона (`CUSTOM_REPORT`, коды атрибуции, имена срезов API — в отчёт не выносить) и без символов `≤`/`≥` (пиши «не больше»/«не меньше»). Деньги — в рублях.

Каждая карточка **открыто отделяет** диагноз (`evidence` — числа+период+объём), рекомендацию (`recommendation`+`where`+`ready_to_use`) и способ перепроверки (`how_to_verify`); `threshold` хранится в `findings.json` для прозрачности (в PDF не печатается). Блок ограничений (`limitations`) — честный список того, что проверить не удалось.

Покажи PDF через ссылку на файл. В чат — сводка топ-5 находок 5-10 строк.

### Почему скилл не вносит изменений сам

Ни на одном шаге скилл не вызывает пишущие тулы. Отключение площадок, добавление минусов, корректировки, паузы — это решения с ценой ошибки: списать запрос в минус или отключить площадку на основе 30 дней легко в сезонной или НЧ-нише, где сегодняшний ноль конверсий — это просто мало данных, а не плохой трафик. Поэтому последнее слово за маркетологом, а скилл даёт ему полную доказательную базу, чтобы решение было быстрым и осознанным.

# Стиль работы

- **Не клянчи.** Один прямой вопрос за раз. В Шаге 0 — единый блок скоупа.
- **Не вываливай простыни.** Сырые отчёты и таблицы — в файлы; в чат сводка 5-10 строк.
- **Гипотеза > пустой вопрос.** «Вот дефолт скоупа — согласен?»
- **Доказательство обязательно.** Каждый флаг = числа + период + объём + порог. Нет объёма данных — пиши «недостаточно данных», не выдумывай вывод.
- **Атрибуция явная, по каждой РК.** Модель берётся отдельно для каждой кампании Директа (нет в настройках — `LSCCD`, последний значимый с кросс-девайсом); та же модель применяется в Метрике через единый словарь Direct↔Метрика, чтобы числа двух систем пересекались по одной логике. Указывай модель (Direct-код + имя Метрики) рядом с каждым конверсионным числом; не сравнивай числа из разных моделей.
- **Деньги в рублях.** В отчётах конвертируй из микро (÷1 000 000); не показывай маркетологу микро-валюту.
- **Только read-only.** Касается и Директа (никаких `*_update`/`*_suspend`), и Метрики (`metrika_api.py` только читает). Если рука тянется внести правку — стоп, это рекомендация в отчёт.
- **Direct и Метрика вместе.** Самые сильные находки — там, где расход из Директа лёг на поведение из Метрики. Если Метрика недоступна (нет токена) — честно помечай выводы как «без поведения».
- **References обязательны.** «Прочти `references/<name>.md`» — это требование, а не намёк.
