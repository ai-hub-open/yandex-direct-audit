# Бриф субагента `bid-segments` — Шаг 5 аудита

> **Это не отдельный скилл, а инструкция для форка.** Оркестратор `yandex-direct-audit`
> запускает изолированного субагента и передаёт ему содержимое этого файла как задачу
> плюс аргументы. Сам по себе файл не запускается.
>
> **Аргументы:** `[slug] [campaign_ids] [период] [KPI]` — далее по тексту `$0`, `$1`, `$2`, `$3`.
>
> **Назначение:** Поиск точек роста через корректировки ставок Яндекс.Директа (устройство/пол-возраст/гео/час). Запускается оркестратором yandex-direct-audit как изолированный субагент на Шаге 5. Тянет текущие корректировки и сегментные срезы CUSTOM_REPORT, нормализует, ищет недо/переэффективные сегменты и возвращает наверх только сводку с конкретными % как гипотезами. Сырьё остаётся в форке. Read-only. Вход — slug аудита, список кампаний, период, KPI.

Ты — изолированный субагент Шага 5 аудита (`bid-segments`). Тебя запустил оркестратор
`yandex-direct-audit`. Истории основного разговора у тебя нет — только эта задача и аргументы.
Собери текущие корректировки и сегментные срезы, переработай и верни наверх **короткую сводку**
с конкретными % как гипотезами, а не простыни. Сырьё срезов остаётся в файлах.

## Read-only — жёстко

Вызывай **только** `yandex_direct_bidmodifiers_get` и `yandex_direct_report_custom` (плюс
Bash/Read/Write для файлов). Список разрешённых тулов тебе не выдан — коннектор называется у
каждого по-своему, поэтому технически пишущие тулы Директа тебе видны.

**Особая осторожность с корректировками:** `bidmodifiers_set`, `bidmodifiers_demographics`,
`bidmodifiers_devices`, `bidmodifiers_regional`, `bidmodifiers_retargeting`, `bidmodifiers_delete` —
это **запись**, несмотря на похожие имена. Не вызывай их. Как и любые `*_add` / `*_update` /
`*_delete` / `*_suspend` / `*_resume` / `*_moderate`.

Корректировки — это **рекомендации**: ставит их маркетолог сам.

## Вход

- `$0` — slug аудита (папка `direct-audits/<slug>/`)
- `$1` — список `campaign_ids`
- `$2` — период (напр. `LAST_30_DAYS` или явные даты)
- `$3` — KPI (целевой CPA и/или ДРР)

Чего нет в аргументах — возьми из `direct-audits/$0/_state.json` (период, `kpi_cpa`, `kpi_drr`,
`counter_id`, `goal_ids`, атрибуция) и `direct-audits/$0/01_account_map.json` (кампании, модели
атрибуции).

## Методология (обязательное чтение)

Прочитай по пути от корня скилла аудита (не резолвится из форка — пробуй путь от корня скилла
`yandex-direct-audit`):

- `references/audit-thresholds.md` — раздел «Корректировки ставок» (когда минус, когда плюс, объём).

- `references/attribution.md` — модели атрибуции и что делать без целей.

## Шаг A. Текущие корректировки + сегментные срезы

Текущие:
```
yandex_direct_bidmodifiers_get({ campaign_ids: $1 })
```

Четыре среза через `yandex_direct_report_custom` (Рецепты 2–5), каждый — отдельный вызов с
`page_limit: 500`, фильтром `Clicks > 0`, `goals` и `attribution_models` из скоупа:

- `Device` → `direct-audits/$0/05_segment_device.tsv`
- `Gender` + `Age` → `05_segment_gender_age.tsv`
- `LocationOfPresenceName` (гео) → `05_segment_geo.tsv`
- `HourOfDay` → `05_segment_hour.tsv`

Поля: `Cost, Clicks, Conversions, CostPerConversion, ConversionRate` **плюс `BounceRate` и
`AvgPageviews`** — поведение сегмента приходит тем же отчётом и понадобится на Шаге C. Для
`HourOfDay` поведенческие поля можно не запрашивать.

**Мост в песочницу:** ответ идёт в твой контекст, а `normalize_report.py` читает файл. Записывай
каждый срез одним блоком:

```
cat > direct-audits/$0/05_segment_device.tsv <<'EOF'
<весь TSV как есть>
EOF
```

Отчёт не собрался за 2 попытки → зафиксируй ограничение по этому срезу и иди к следующему, не
выдумывай данные.

## Шаг B. Поиск сегментов под корректировку

Нормализуй каждый срез:
```
python -m scripts.normalize_report --input direct-audits/$0/05_segment_device.tsv --kpi-cpa <X>
```

- **Минус-корректировка:** сегмент заметно тратит, но CPA выше KPI / ноль конверсий при заметном расходе.
- **Плюс-корректировка:** сегмент перевыполняет (CPA ниже KPI, высокий CR).
- ⚠️ **Объём:** сегмент с **<~10 конверсий** за период — «гипотеза, накопить данные», не основание
  для агрессивной корректировки. Конкретный % давай как стартовую гипотезу.
- Сверь с уже выставленными (`bidmodifiers_get`) — не предлагай то, что уже стоит.
- Для гео регион называй **именем** («Москва», «Свердловская область») — оно пришло в
  `LocationOfPresenceName`. Числовой `region_id` не нужен: маркетолог ставит корректировку в
  интерфейсе, выбирая регион из списка по названию. Справочник регионов не тяни.

## Шаг C. Поведение как обоснование %

`BounceRate` и `AvgPageviews` пришли теми же срезами Шага A. Используй их, чтобы рекомендация по %
опиралась не только на цену клика:

«Мобайл — 68% расхода, CPA 2 300 ₽, отказы 70% против 35% на десктопе → MOBILE −20% обоснована
поведением, а не только ценой клика».

Колонки пустые (счётчик к кампании не привязан) → пометь «без поведения», % давай по CPA и объёму.

## Артефакты

- `direct-audits/$0/05_bid_modifier_opportunities.md` — по каждому сегменту: расход, конверсии, CPA,
  рекомендуемый %, пометка объёма. Это **рекомендации**, не правки.
- `direct-audits/$0/05_bid_modifier_opportunities.json` — машиночитаемый.

## Что вернуть наверх (КРИТИЧНО)

Сырьё срезов НЕ выводи. Верни **только это**, ≤ 20 строк:

```
СВОДКА ШАГА 5 — Корректировки ставок (slug: $0)
- Сегментов с рекомендацией: минус N / плюс M
- Топ: 1) <сегмент> CPA <₽> → <−/+X%> 2) ... 3) ...
- Где данных мало (гипотезы): <список>
- Артефакты: 05_bid_modifier_opportunities.{md,json}, 05_segment_*.tsv
- ⚠️ Ограничения: <срез не собрался за 2 попытки / без поведения (счётчик не привязан) / мало данных>
```

Оркестратор покажет сводку человеку на гейте Шага 5. % — стартовые гипотезы, не истина; ставит
корректировки человек в основном контексте.
