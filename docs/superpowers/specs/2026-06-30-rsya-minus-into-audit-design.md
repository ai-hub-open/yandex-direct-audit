# Дизайн: внедрение rsya-minus в yandex-direct-audit через `context: fork` и субагентов

> Статус: согласован с пользователем (2026-06-30). Реализация — в плане рядом.
> Язык артефактов и общения — русский, аудитория — маркетолог, не разработчик.

## 1. Цель и контекст

Скилл **yandex-direct-audit** (7-шаговый read-only аудит Яндекс.Директа) перестраивается по
архитектуре эталонного скилла **marketing-strategist v5**: оркестратор в основном контексте +
изолированные **форк-субагенты** (`context: fork`) на тяжёлых шагах сбора данных. Логика
отдельного скилла **yandex-direct-rsya-minus** (углублённая минусация площадок РСЯ) целиком
переносится внутрь аудита и становится мозгом Шага 4.

**Проблема, которую решаем.** Тяжёлые шаги аудита (поисковые запросы, площадки РСЯ, сегменты
ставок) возвращают из Директа гигантские TSV-отчёты. Сейчас всё это сырьё оседает в основном
контексте и вытесняет ранние решения к моменту сборки финального отчёта (Шаг 7). На больших
аккаунтах аудит «захлёбывается».

**Решение.** Вынести эти три шага в изолированные субагенты. Субагент собирает «грязное» сырьё
в своём контексте, пишет файлы-артефакты на диск и возвращает наверх **только сводку ≤20 строк**.
Решение и гейты остаются за человеком в основном контексте. Read-only дисциплина сохраняется.

## 2. Решения, согласованные с пользователем

1. **Объём форка:** изолируем **Шаги 3, 4 и 5** (поисковые запросы / площадки РСЯ / сегменты ставок).
2. **rsya-minus:** его логику **полностью вносим в аудит**. При этом **репозиторий
   `E:\AI\yandex-direct-rsya-minus` НЕ трогаем — он остаётся неизменным** (read-only источник, из
   которого только копируем файлы; никаких правок, пометок DEPRECATED или удаления там не делаем).
3. **НДС:** считаем **с НДС** (`IncludeVAT: YES`) — это реальные деньги, которые платит рекламодатель.
   Политика НДС в аудите стандартизируется на YES во всех отчётах, где это в нашем контроле, чтобы
   расход по площадкам сходился с расходом по кампаниям.

## 3. Эталонный паттерн (из marketing-strategist v5) — что копируем

Из изученного эталона переносим в аудит ровно эти приёмы:

- **Оркестратор + субагенты.** Лёгкие шаги (решения, гейты, синтез) — инлайн в оркестраторе.
  Тяжёлый сбор данных — в форк-субагенте.
- **Frontmatter субагента:** `context: fork`, `agent: general-purpose`, `disable-model-invocation: true`,
  `allowed-tools: <список>`, `argument-hint: [...]`. Имя и `description`, поясняющий, что субагента
  запускает оркестратор аудита и что он возвращает только сводку.
- **Тело субагента — проза:** «Ты изолированный субагент, истории основного разговора у тебя нет,
  только эта задача и аргументы. Собери сырьё → переработай → верни ≤20 строк, файлы оставь на диске.»
- **Принцип возврата:** наверх — компактная сводка; сырьё (полные TSV) остаётся в файлах.
- **Фолбек:** если форк недоступен (старая среда / ошибка форка / путь не резолвится) — оркестратор
  выполняет шаг **инлайн** по тем же reference/scripts. Делегирование — оптимизация, не зависимость.

## 4. Целевая архитектура аудита

```
yandex-direct-audit/  (оркестратор)
├── SKILL.md                       # + раздел «Архитектура: оркестратор + субагенты»; Шаги 3/4/5 переписаны на делегирование
├── README.md                      # НОВЫЙ — навигация по пакету (как в marketing-strategist)
├── references/
│   ├── mcp-tools-map.md
│   ├── metrika-integration.md
│   ├── audit-thresholds.md        # раздел «Площадки РСЯ» дополняется ссылкой на ruleset минусации
│   ├── optimization-playbook.md
│   ├── custom-report-recipes.md   # Рецепт 1 (площадки) сверен с rsya-minus; IncludeVAT NO → YES
│   ├── report-template.md
│   └── rsya-minus-rules.md         # НОВЫЙ — полный ruleset порогов минусации (перенос minus-rules.md)
├── subagents/                      # НОВАЯ ПАПКА — форк-субагенты
│   ├── search-queries/SKILL.md     # Шаг 3
│   ├── rsya-placements/SKILL.md    # Шаг 4 (ядро rsya-minus)
│   └── bid-segments/SKILL.md       # Шаг 5
├── scripts/
│   ├── __init__.py
│   ├── normalize_report.py
│   ├── metrika_api.py
│   ├── render_report.py
│   └── analyze_placements.py       # НОВЫЙ — перенос из rsya-minus
├── assets/
│   ├── findings_schema_example.json
│   └── placement_patterns.json     # НОВЫЙ — перенос из rsya-minus
└── evals/evals.json                # дополнен проверками изоляции субагентов + minus_list.txt
```

**Единый источник истины.** References и scripts держим **централизованно в аудите** (пользователь
выбрал «одну точку правды»). Субагенты читают их по пути от корня скилла аудита; копий внутри
`subagents/` не держим. Если относительный путь из форка не резолвится — субагент пробует путь от
корня скилла, а в крайнем случае срабатывает фолбек «оркестратор делает шаг инлайн».

## 5. Субагенты — детальный дизайн

Общее для всех трёх:
- `context: fork`, `agent: general-purpose`, `disable-model-invocation: true`.
- **Read-only** набор `allowed-tools`: только нужные `*_get` / `report_*` / `dictionaries_*` /
  `yandex_direct_api_call` (исключительно для GET-отчётов) + `Bash Read Write Grep Glob` (Bash — чтобы
  запускать python-скрипты). Никаких `*_add/update/delete/suspend/resume/moderate` и
  `bidmodifiers_demographics`. Запрет дублируется в прозе тела.
- Вход: позиционные аргументы (`$0` slug и т.д.); чего нет в аргументах — субагент берёт из
  `direct-audits/<slug>/_state.json` и `01_account_map.json`.
- Деньги: **с НДС**; конвертация микро→рубли как в аудите (сверка `Cost`, при рублях — `--money-in-rub`).
- Атрибуция: модель берётся по каждой кампании из `01_account_map.json` (нет — `LSCCD`).
- Возврат наверх: блок ≤20 строк по фиксированному формату (см. ниже). Оркестратор показывает его
  на гейте и принимает решение с человеком.

### 5.1. Субагент `search-queries` (Шаг 3 — майнинг поисковых запросов)

- **Вход:** `$0` slug, `$1` список campaign_ids поисковых кампаний (или «все поисковые»), период.
- **allowed-tools:** `yandex_direct_report_search_queries Bash Read Write Grep Glob`.
- **Делает:** тянет `report_search_queries` (огромный TSV) → `normalize_report.py` → кандидаты в
  минус (расход без конверсий / высокий отказ; **не** трогаем запросы с <5 переходов) →
  обогащает поведением из Метрики (`metrika_api.py --preset queries`) → группирует по
  повторяющимся словам/темам.
- **Reference (читает по пути от корня скилла):** раздел «Поисковые запросы → минусация» в
  `audit-thresholds.md`; «ПОИСК → Минусовка» в `optimization-playbook.md`; queries-часть
  `metrika-integration.md`.
- **Артефакты:** `03_negative_candidates.md` + `03_negative_candidates.json`.
- **Возврат:** сколько кандидатов, топ-темы групп, оценка экономии, пути к артефактам, ⚠️-пробелы.

### 5.2. Субагент `rsya-placements` (Шаг 4 — ядро rsya-minus)

- **Вход:** `$0` slug, `$1` список сетевых campaign_ids, период, tCPA (или tcpa-map), цели, атрибуция.
- **allowed-tools:** `yandex_direct_api_call yandex_direct_campaigns_get yandex_direct_report_campaign Bash Read Write Grep Glob`.
- **Делает:**
  1. Собирает `CUSTOM_REPORT` по площадкам через `yandex_direct_api_call` (поля и фильтры —
     `custom-report-recipes.md` Рецепт 1, сверенный с rsya-report.md: `AdNetworkType = AD_NETWORK`,
     `Impressions > 0`, `IncludeVAT: YES`). Сохраняет сырьё как `04_placements.tsv`.
  2. ⚠️ **Фолбек MCP:** если `api_call` не достаёт до `/json/v5/reports` — фиксирует ограничение,
     собирает что может из `report_campaign` со срезом `AdNetworkType`, не выдумывает площадки.
  3. Прогоняет `scripts/analyze_placements.py` (умный анализатор из rsya-minus: свёртка до уровня
     площадки, пороги от tCPA, словарь мусорных/watch-имён `assets/placement_patterns.json`,
     раздельный гейт объёма, категории 🔴/🟠/🟡/✅/⚪).
  4. Обогащает поведением из Метрики (`metrika_api.py --preset placements`, джойн по
     `DirectPlatform` ↔ `Placement`).
- **Reference:** `rsya-minus-rules.md` (полный ruleset), `custom-report-recipes.md` (Рецепт 1),
  placements-часть `metrika-integration.md`.
- **Артефакты:** `04_placement_candidates.md` + `04_placement_candidates.json` (для финального
  отчёта аудита) **и** готовый к вставке `minus_list.txt` (по кампаниям, 🔴+🟠 — главный actionable
  rsya-minus). Механика: `analyze_placements.py` запускаем с `--outdir direct-audits/<slug>` (он
  пишет `candidates.json` / `minus_list.txt` / `report.md`); затем субагент **переименовывает**
  `candidates.json` → `04_placement_candidates.json` и `report.md` → `04_placement_candidates.md`,
  а `minus_list.txt` оставляет под этим же именем. Так Шаг 7 получает ожидаемые имена входов, а
  маркетолог — готовый список для вставки.
- **Возврат:** счётчики 🔴/🟠/🟡/✅/⚪, оценка экономии (расход на площадках под минус без конверсий),
  3-5 самых дорогих кандидатов с причиной, пути к артефактам (включая `minus_list.txt`), ⚠️-пробелы.

### 5.3. Субагент `bid-segments` (Шаг 5 — корректировки ставок)

- **Вход:** `$0` slug, `$1` campaign_ids, период, KPI (tCPA/ДРР), counter_id/goal_ids.
- **allowed-tools:** `yandex_direct_api_call yandex_direct_bidmodifiers_get yandex_direct_dictionaries_regions Bash Read Write Grep Glob`.
- **Делает:** текущие корректировки (`bidmodifiers_get`) + срезы Device / Gender+Age /
  LocationOfPresenceName / HourOfDay через `CUSTOM_REPORT` (Рецепты 2–5) → `normalize_report.py` →
  ищет сегменты «много тратит, плохо конвертит» (минус-корректировка) и «перевыполняет» (плюс);
  при гео-рекомендации — расшифровка region_id через `dictionaries_regions` (кэш `_regions_cache.json`);
  обогащает поведением из Метрики (`metrika_api.py --preset segments --segment ...`). Сегменты с
  <~10 конверсий — помечает «гипотеза, нужно накопить».
- **Reference:** «Корректировки ставок» в `audit-thresholds.md`; «ОБЩЕЕ → Корректировки ставок» в
  `optimization-playbook.md`; Рецепты 2–6 в `custom-report-recipes.md`; segments-часть `metrika-integration.md`.
- **Артефакты:** `05_bid_modifier_opportunities.md` + `05_bid_modifier_opportunities.json`.
- **Возврат:** какие сегменты под минус/плюс с конкретными %, где данных мало, пути к артефактам.

### 5.4. Формат возврата (общий шаблон ≤20 строк)

```
СВОДКА ШАГА N — <название> (slug: <slug>)
- <2-5 ключевых числовых выводов>
- Оценка экономии/роста: <₽>
- Топ-кандидаты: 1) ... 2) ... 3) ...
- Артефакты: <файлы>
- ⚠️ Пробелы/ограничения: <Метрика недоступна / api_call не достаёт reports / мало данных>
```

|---|---|---|
| `scripts/analyze_placements.py` | `scripts/analyze_placements.py` | без правок логики; проверить, что `skill_dir` находит `assets/placement_patterns.json` в аудите (два уровня вверх от `scripts/`) |
| `assets/placement_patterns.json` | `assets/placement_patterns.json` | без правок |
| `references/minus-rules.md` | `references/rsya-minus-rules.md` | без правок содержания; поправить упоминания «этот скилл» на контекст Шага 4 аудита |
| тело отчёта из `references/rsya-report.md` | вмердживается в `custom-report-recipes.md` Рецепт 1 | согласовать поля и `IncludeVAT: YES` |

`metrika_api.py`, `normalize_report.py`, `render_report.py` в аудите уже есть — не дублируем.

## 7. Политика НДС (с НДС везде)

- `custom-report-recipes.md`: общая форма и Рецепты 1–5 — `IncludeVAT: NO` → **`YES`**.
- Шаг 4 (`rsya-placements`) — `YES` (как в исходном rsya-minus).
- Дедикейтед report-тулы (Шаги 2, 3, 6): параметр `IncludeVAT` может быть зашит в обёртке MCP.
  **На реализации проверить**, отдаёт ли обёртка управление НДС. Если да — выставить `YES`; если
  нет и обёртка отдаёт без НДС — зафиксировать это в блоке ограничений отчёта (расхождение ~×1.2
  между «с НДС» по площадкам и «без НДС» по кампаниям) и пояснить маркетологу.
- В SKILL.md и `report-template.md` обновить формулировки «расход с НДС».

## 8. Карта артефактов и Шаг 7 (без изменений по существу)

Имена артефактов Шагов 3/4/5 сохраняются (`03_/04_/05_*`), поэтому Шаг 7 (сборка `findings.json` →
`render_report.py` → PDF) получает те же входы и переписывать его не нужно. Дополнительно поле
`ready_to_use` находок по площадкам наполняется из `minus_list.txt`. Карта артефактов в SKILL.md
дополняется пометкой, какие шаги исполняются субагентами.

## 9. Read-only дисциплина

Сохраняется на всех уровнях: оркестратор и все три субагента вызывают только read-only тулы.
`allowed-tools` субагентов физически не содержат пишущих тулов; запрет продублирован прозой.
Любой соблазн «просто отключить площадку/добавить минус» → строка-рекомендация в отчёте, не действие.

## 10. evals

`evals/evals.json` дополняется ожиданиями:
- Шаги 3/4/5 исполняются изолированными субагентами (`context: fork`), наверх возвращается сводка,
  сырьё не вываливается в чат.
- Шаг 4 отдаёт готовый `minus_list.txt` по кампаниям (🔴+🟠).
- Read-only сохраняется внутри субагентов (ни одного пишущего вызова).
- Фолбек: при недоступности форка шаг выполняется инлайн по тем же reference.
Существующие 4 кейса остаются валидными (логика шагов не меняется, меняется только место исполнения).

## 11. Что НЕ входит в объём (YAGNI)

- Шаги 0, 1, 2, 6, 7 по существу не меняются (Шаг 2 ведёт гейт и остаётся инлайн; Шаг 7 — та же сборка).
- Упаковщик/`.skill`/install-скрипт не добавляем (отдельный шаг пользователя при необходимости).
- Репозиторий `yandex-direct-rsya-minus` не редактируем и не удаляем.
- Запись в аккаунт Директа не добавляем — скилл остаётся read-only.

## 12. Проверить на реализации

1. Резолв путей к `references/` и `scripts/` из форк-субагента; при провале — путь от корня скилла,
   затем фолбек на инлайн.
2. `analyze_placements.py` находит `assets/placement_patterns.json` в новом расположении.
3. Управляемость `IncludeVAT` для дедикейтед report-тулов (см. §7).
4. Точное имя поля модели атрибуции на кампании (обёртки различаются — SKILL уже это хеджирует).
5. Наличие `yandex_direct_api_call` в рантайме MCP; если нет — отрабатывает фолбек §5.2.3.
