# Замечания к yandex-direct-mcp (по итогам сборки Desktop-профиля аудита)

Найдено при адаптации скилла `yandex-direct-audit` под Claude Desktop + ClickProxy-коннектор
(`https://direct-mcp.aihub.click.ru/c/<логин>/<токен>/<ID>`). Скилл обходит все три пункта на своей
стороне, но обход стоит денег и точности — чинить лучше в сервере.

Ссылки на код даны по состоянию репозитория D:\yandex-direct-mcp на момент разбора.

---

## 1. Ретрай офлайн-отчёта не работает — каждый повтор создаёт новый отчёт

**Где:** `src/client.ts:470` (текст ошибки) против `src/tools/reports.ts:66` (генерация имени).

При офлайн-очереди клиент возвращает `status: "processing"` и советует:

> «Повторите тот же запрос через N с — готовый отчёт вернётся из очереди.»

Но `buildReportParams` дописывает к имени отчёта уникальный суффикс **на каждом вызове**:

```ts
ReportName: `${opts.reportName} ${Date.now().toString(36)}-${Math.random().toString(36).slice(2, 8)}`,
```

В Reports API отчёт в очереди адресуется именем. Значит «тот же запрос» уходит под **новым**
именем и ставит в очередь **новый** отчёт, а прежний остаётся висеть. Очередь Директа — 5 слотов,
так что несколько добросовестных ретраев её забивают, и забрать уже готовый отчёт нельзя в
принципе. Параметр `report_name` не спасает: суффикс дописывается и к нему.

**Как чинит скилл:** не больше 2 повторов и чанкинг отчётов по кампаниям, чтобы они возвращались
сразу и не попадали в очередь. Это лишние вызовы и лишние баллы квоты.

**Что предлагаю:** если `report_name` задан явно — не трогать его. Тогда клиент может повторить
запрос тем же именем и забрать готовый отчёт, как обещает сообщение об ошибке.

## 2. `Bun.serve` без `idleTimeout` при 90-секундном ожидании отчёта

**Где:** `src/transports/http.ts:94` (вызов `Bun.serve`), `src/client.ts:438` (бюджет ожидания).

Сервер ждёт готовности отчёта **внутри** HTTP-запроса, до 90 секунд по умолчанию. Всё это время по
сокету ничего не идёт. При этом `Bun.serve` вызывается без `idleTimeout`, а его дефолт — 10 секунд
(`bun-types/serve.d.ts`). Похоже на самую вероятную причину сценария «через stdio отчёты работают,
через хостинг — рвутся».

Это вывод из кода и типов, не из воспроизведения — стоит проверить живьём, прежде чем чинить.

Сверху добавляются свои таймауты обратного прокси (в `docker-compose.yml` это Coolify/Traefik) и
клиента Claude. Максимум `idleTimeout` у Bun — 255 с, то есть даже явная настройка не покроет
самые долгие отчёты; для них нужен асинхронный режим (отдать `report_id`, забирать отдельным
вызовом).

**Как обходит скилл:** `wait_seconds: 55` и мелкие отчёты.

## 3. В enum `attribution_models` нет `LYDC` / `LYDCCD`

**Где:** `src/tools/reports.ts:117`.

```ts
attribution_models: { items: { enum: ["FC","LC","LSC","FCCD","LCCD","LSCCD","AUTO"] } }
```

Директ поддерживает ещё «последний переход из Директа» (`LYDC`) и его кросс-девайс-вариант
(`LYDCCD`). Для аудита это как раз модель, отвечающая на вопрос «сколько конверсий принёс именно
Директ», — самый частый аргумент в разговоре с рекламодателем.

**Как обходит скилл:** для кросс-чека воронки берёт `FC` (первый переход) — вывод получается тот
же, но формулировка слабее.

## 4. Запрос фичи: `save_to` у report-тулов

Не баг, а то, что снимет самое дорогое место всей связки.

Сейчас TSV-ответ приходит **в контекст модели**, а анализаторы скилла (`analyze_placements.py`,
`run_analysis.py`) читают файл с диска. Общей файловой системы между ними нет, поэтому модель
вынуждена переписывать весь отчёт в файл руками — десятки тысяч токенов на каждый шаг. Именно
из-за этого в скилле появились жёсткие `page_limit`, обязательный фильтр `Clicks > 0` и запрет
добавлять `Device`/`LocationOfPresenceName` в отчёт по площадкам.

**Предложение:** параметр `save_to: "<путь>"` у report-тулов. Сервер пишет TSV на диск и возвращает
компактный ответ: путь, число строк, заголовок и первые N строк. Модель видит форму данных, файл
уходит анализатору напрямую, контекст не тратится.

Оговорка: полезно только там, где сервер и клиент делят файловую систему (локальный stdio из
Claude Code). Для хостинга нужен другой канал — например, отдавать ссылку на скачивание.
