# Карта инструментов MCP yandex-direct (read-only режим аудита)

Этот reference описывает, какие тулы твоего MCP `yandex-direct` использует скилл аудита, как звать сырой `api_call` для отчётных срезов, которых нет в дедикейтед тулах, и какие у MCP ограничения (главное — он **Direct-only**, Метрики в нём нет).

## Проверка доступности

Перед началом убедись, что в сессии есть `mcp__yandex-direct__*` тулы. Точные имена и схемы аргументов смотри в списке тулов MCP в рантайме (README группирует их, но имена аргументов могут отличаться). Если тулов нет — live-аудит невозможен, сообщи маркетологу.

## Разрешённые (read-only) тулы

Скилл вызывает **только** эти. Они ничего не меняют в аккаунте.

| Тул | Назначение в аудите | Шаг |
|---|---|---|
| `yandex_direct_campaigns_get` | Инвентаризация: типы, статусы, стратегии, счётчики, бюджеты, минусы | 1 |
| `yandex_direct_adgroups_get` | Вложенность групп (при необходимости) | 1 |
| `yandex_direct_ads_get` | Состав объявлений в группах (при необходимости) | 6 |
| `yandex_direct_keywords_get` | Ключи для проверки кросс-минусовки и дедупликации | 6 |
| `yandex_direct_bidmodifiers_get` | Текущие корректировки ставок | 5 |
| `yandex_direct_report_campaign` | Статистика по кампаниям | 2 |
| `yandex_direct_report_ad` | Статистика по объявлениям | 6 |
| `yandex_direct_report_search_queries` | Поисковые запросы → минус-кандидаты | 3 |
| `yandex_direct_dictionaries_regions` | Расшифровка region_id (кэшировать) | 1/5 |
| `yandex_direct_api_call` | **Только отчётные** CUSTOM_REPORT-запросы (площадки, сегменты) | 4/5 |

## ЗАПРЕЩЁННЫЕ тулы (скилл их не вызывает никогда)

`campaigns_add/update/delete/suspend/resume`, `adgroups_add/update/delete`, `ads_add/update/delete/suspend/resume/moderate`, `adimages_add`, `keywords_add/update/delete/suspend/resume`, `bidmodifiers_demographics` (это запись). И **любой** `yandex_direct_api_call`, который не является GET-отчётом (т.е. с методами `add/update/delete/set/suspend/resume`).

Если по логике задачи кажется, что нужно «просто отключить площадку» — **нет**. Это строка в отчёте-рекомендации. Внедряет маркетолог.

## Сырой `api_call` для отчётных срезов

Дедикейтед report-тулы покрывают `campaign / ad / search_queries`. Для срезов по `Placement`, `Device`, `Gender`, `Age`, `LocationOfPresenceName`, часу суток — нужен `CUSTOM_REPORT`, которого в обёртках нет. Собираем его через `yandex_direct_api_call` к эндпоинту отчётов. Готовые тела запросов — в `custom-report-recipes.md`.

⚠️ **Критическая проверка:** убедись, что `yandex_direct_api_call` твоего MCP умеет ходить на `/json/v5/reports` (у отчётов отдельный эндпоинт и формат TSV, отличный от обычных JSON-сервисов). Если обёртка проксирует только обычные сервисы (`/json/v5/<service>`) и **не достаёт** до reports:
1. Зафиксируй это в отчёте как ограничение.
2. Собери что можно из `report_campaign`/`report_ad` со срезом `AdNetworkType`.
3. Порекомендуй маркетологу расширить reports-тул MCP (добавить CUSTOM_REPORT с произвольными `FieldNames`).
Не выдумывай данные по площадкам/сегментам, если их негде взять.

## Метрика — через скрипт, не через MCP

Этот MCP — **Direct-only**. Поведение и правда про конверсии берутся из Яндекс.Метрики через `scripts/metrika_api.py` (read-only, OAuth-токен в окружении), а не через MCP. Методология и мост Direct↔Метрика — в `references/metrika-integration.md`. Поэтому:

- Конверсионные/поведенческие поля **Direct-отчётов** (`Conversions`, `BounceRate`, `AvgPageviews`) всё ещё зависят от привязки счётчика к кампании — если связки нет, они пусты, и это находка high (без целей нет оптимизации). Но саму поведенческую глубину (отказ/глубина по площадке, запросу, сегменту) теперь даёт Метрика напрямую, даже там, где Direct-отчёт молчит.
- Per-placement отказы, которых раньше не было, теперь доступны: `metrika_api.py --preset placements` = аналог отчёта «Директ, площадки».
- Если токена Метрики нет (`YANDEX_METRIKA_TOKEN`/`YANDEX_DIRECT_TOKEN` со скоупом `metrika:read`) — аудит идёт по Директу, а поведенческие выводы помечаются «без Метрики». Подключение токена — самый быстрый способ повысить точность.

## ЕПК (UNIFIED_CAMPAIGN)

С конца 2024 Единая перформанс-кампания заменила отдельные ТГО/динамику/смарт-баннеры. Управление — через эндпоинт `v501` (в `api_call` — `api_version: "v501"`). По ЕПК часть срезов на уровне критериев беднее (для кампаний, собранных Мастером, `CriteriaId`/имя могут не отдаваться). Детекть `Type = UNIFIED_CAMPAIGN` и анализируй как смешанное размещение Поиск+Сеть+товарные; не жди от неё той же гранулярности, что от классического Поиска.

## Деньги в микро-валюте

Все денежные поля Direct API — в микро (1 000 000 = 1 ₽). `Bid: 300000` = 0.30 ₽. В отчётах для маркетолога **всегда** конвертируй в рубли (÷1 000 000). `scripts/normalize_report.py` делает это сам.

## Бюджет квот (units / баллы)

- Ошибочный вызов метода стоит ~20 баллов — не долби API в цикле при ошибках.
- Reports: не более 20 запросов к сервису за 10 секунд, не более 5 офлайн-отчётов в очереди; статистика — за последние 3 года.
- Справочник `dictionaries_regions` ~3 МБ — звать один раз, кэшировать в `_regions_cache.json`, грепать по имени, не читать целиком.
- Типичный аудит (campaigns_get + report_campaign + search_queries + 2-3 CUSTOM_REPORT + bidmodifiers_get) укладывается в сотни-тысячи баллов. Не перезапрашивай то, что уже в артефактах за тот же период.

## Ошибки и фолбеки

- **MCP не отвечает / `{success:false}` / `isError:true`** — обработай по месту: отметь шаг как неполный в отчёте, продолжай по остальным данным, не падай целиком.
- **Пустой `campaigns_get`** — аккаунт пуст или не тот логин; уточни `Client-Login` у маркетолога.
- **`api_call` не достаёт reports** — см. раздел про сырой api_call выше.
- **Поля конверсий пусты везде** — нет связки с Метрикой по всему аккаунту; это находка №1, не баг.
- **Сезонность/мало данных** — расширь период или явно помечай выводы как «гипотеза».
