# Коннектор Яндекс.Директа: подключение, тулы, правила отчётов

Скилл работает через **MCP-коннектор Директа** (JSON API v5/v501) — read-only набор вызовов. Этот reference описывает: как коннектор подключить, какие тулы разрешены, как собирать CUSTOM_REPORT и как не утопить контекст в гигантских отчётах.

---

## Как подключить коннектор

Если в сессии нет тулов Директа — **процитируй маркетологу этот блок целиком и остановись**. Без коннектора live-аудит невозможен, продолжать нечего.

> **Claude Desktop / claude.ai → Settings → Connectors → Add custom connector** → любое имя → в поле адреса:
>
> ```
> https://direct-mcp.aihub.click.ru/c/<токен click.ru>
> ```
>
> - `<токен click.ru>` — профиль click.ru (https://click.ru/userinfo.html) → поле **API Token** → скопировать или **Создать**. Токен — из того аккаунта click.ru, где подключён кабинет Директа. «Пересоздать» — только при утечке: старые подключения перестанут работать.
> - Закрепить один кабинет: `https://direct-mcp.aihub.click.ru/c/<токен click.ru>/<кабинет>` — логин Директа, название или ID в click.ru (`@` → `%40`, пробел → `%20`).
> - Кабинет создан напрямую в Яндексе, без click.ru: `https://direct-mcp.aihub.click.ru/y/<OAuth-токен Яндекса>`.
>
> Затем **Continue → Add** и перезапуск Claude Desktop. Больше ничего заполнять не нужно: ни заголовков, ни логина-пароля. Адрес и есть вся авторизация. Claude Code: `claude mcp add --scope user --transport http yandex-direct "<адрес>"`.
>
> Проверка: в сессии появились тулы `yandex_direct_*`. Подробнее — https://help.click.ru/7738
>
> ⚠️ **Этот адрес равносилен паролю.** Токен в нём открывает Директ, Вордстат, Метрику и VK Рекламу этого аккаунта click.ru. Не пересылай ссылку в чатах и переписке; при утечке — пересоздай токен в профиле click.ru.

Старую форму `/c/<логин>/<токен>/<ID пользователя>` сервер ещё принимает, поэтому у давних пользователей она может работать — менять её не заставляй, но новым не выдавай.

### Мультиаккаунт

Адрес `/c/<токен>` без кабинета открывает все кабинеты токена; адрес с кабинетом задаёт кабинет по умолчанию. Если кабинета в адресе нет, а у токена **несколько** кабинетов — дефолта нет вовсе: любой вызов без `client_login` падает с «Кабинет не указан, а у токена их несколько (N)». Поэтому предполётка начинается с `accounts_get`. Кроме того:

- `yandex_direct_accounts_get` покажет кабинеты, доступные этому токену Click.ru;
- **любой** тул принимает `client_login: "<другой логин>"` — вызов уйдёт в другой кабинет с тем же токеном.

Если аудит идёт по одному кабинету — `client_login` не передавай, хватит адреса коннектора.

## Проверка доступности

**Имя коннектора задаёт пользователь**, поэтому префикс тулов заранее неизвестен (`YAD-Original`, `YadLisa`, `yad_gossa` — всё это разные валидные имена). Ищи тулы **по суффиксу имени**: `…yandex_direct_campaigns_get`, `…yandex_direct_report_custom`. Никогда не хардкодь префикс.

⚠️ **Наличие тула ≠ рабочий доступ.** Тул может быть загружен, но с протухшим токеном Click.ru или не тем логином в адресе. Поэтому на Шаге 0 скилл делает **живой предполётный пробник** — см. раздел «Предполётная проверка доступов» Шага 0.

## Разрешённые (read-only) тулы

Скилл вызывает **только** эти. Они ничего не меняют в аккаунте.

| Тул | Назначение в аудите | Шаг |
|---|---|---|
| `yandex_direct_accounts_get` | Список доступных кабинетов (при мультиаккаунте) | 0 |
| `yandex_direct_campaigns_get` | Инвентаризация: типы, статусы, стратегии, счётчики, бюджеты, минусы | 0/1 |
| `yandex_direct_adgroups_get` | Вложенность групп (при необходимости) | 1 |
| `yandex_direct_ads_get` | Состав объявлений в группах (при необходимости) | 6 |
| `yandex_direct_keywords_get` | Ключи для проверки кросс-минусовки и дедупликации | 6 |
| `yandex_direct_bidmodifiers_get` | Текущие корректировки ставок | 5 |
| `yandex_direct_report_campaign` | Статистика по кампаниям | 0/2 |
| `yandex_direct_report_ad` | Статистика по объявлениям | 6 |
| `yandex_direct_report_search_queries` | Поисковые запросы → минус-кандидаты | 3 |
| `yandex_direct_report_custom` | Произвольные срезы: площадки, устройства, гео, пол/возраст, часы | 4/5 |

## ЗАПРЕЩЁННЫЕ тулы (скилл их не вызывает никогда)

`campaigns_add/update/delete/suspend/resume`, `adgroups_add/update/delete`, `ads_add/update/delete/suspend/resume/moderate`, `adimages_add`, `keywords_add/update/delete/suspend/resume`, `keywordbids_set`, `bidmodifiers_set/delete/demographics/devices/regional/retargeting`, `sitelinks_add/delete`, `adextensions_add/delete`.

Если по логике задачи кажется, что нужно «просто отключить площадку» — **нет**. Это строка в отчёте-рекомендации. Внедряет маркетолог.

## CUSTOM_REPORT через `report_custom`

Дедикейтед report-тулы покрывают `campaign / ad / search_queries`. Срезы по `Placement`, `Device`, `Gender`, `Age`, `LocationOfPresenceName`, `HourOfDay` собираются тулом `yandex_direct_report_custom` с `report_type: "CUSTOM_REPORT"`. Готовые наборы полей — в `custom-report-recipes.md`.

Тул принимает **обычные параметры**, а не сырое тело API. Если встретишь в старых заметках JSON вида `{"params": {"FieldNames": …}}` — переводи по таблице:

| Сырое тело API Директа | Параметр `report_custom` |
|---|---|
| `ReportType` | `report_type` (`"CUSTOM_REPORT"`) |
| `FieldNames` | `fields` |
| `SelectionCriteria.Filter: [{Field, Operator, Values}]` | `filters: [{field, operator, values}]` |
| фильтр по `CampaignId IN` | `campaign_ids: [<int>]` |
| `DateFrom` / `DateTo` / `DateRangeType` | `date_from` / `date_to`, либо `date_range` |
| `IncludeVAT: "YES"` | `include_vat: true` — **это дефолт**, передавать не нужно |
| `Goals` | `goals: [<int>]` |
| `AttributionModels` | `attribution_models: ["LSCCD", …]` |
| `Page.Limit` | `page_limit` |
| `ReportName` | не передавать — имя уникализируется на стороне коннектора |
| заголовок `Client-Login` | `client_login` (есть у любого тула) |
| — | `wait_seconds` — сколько ждать офлайн-очередь |

Те же параметры работают и у `report_campaign` / `report_ad` / `report_search_queries`: там достаточно переопределить `fields`.

## Правила объёма отчётов (обязательные)

Ответ тула приходит **в контекст модели**, а python-анализаторы читают файл из песочницы — общей файловой системы между ними нет. Значит, любой отчёт придётся переписать в файл руками, и его размер оплачивается контекстом. Отсюда жёсткие правила:

### 1. Адаптивный чанкинг

- **≤5 кампаний в скоупе** — один отчёт на весь скоуп.
- **>5 кампаний** — один отчёт = одна кампания (`campaign_ids: [<id>]`), последовательно. Мелкие отчёты чаще отдаются сразу и не уходят в офлайн-очередь.

### 2. Душить объём на стороне API, а не после

- `campaigns_get` — без архива: `states: ["ON","OFF","SUSPENDED"]`; архивные — только точечно по `ids` из отчёта с расходом.
- Деньги в `campaigns_get` (лимиты, ставки, ценность целей) — **в микро**, в отчётах — в рублях.

- Всегда `page_limit`: запросы — 5000, площадки — 3000, сегменты — 500.
- Всегда фильтры `Impressions > 0` **и** `Clicks > 0` — строки без кликов не несут ни расхода, ни вывода.
- Только нужные поля. Каждый лишний срез в `fields` умножает число строк: добавил `Device` — получил до 4 строк вместо одной, добавил ещё и гео — до сотни.

Соблазн «взять пошире, вдруг пригодится» здесь стоит дороже, чем кажется: это не лишние килобайты на диске, а лишние десятки тысяч токенов, после которых форку не хватит места на сам анализ.

### 3. Офлайн-очередь

Отчёт может уйти в очередь — тул вернёт `status: "processing"`. Тогда:

- `wait_seconds: 55` на всех тяжёлых отчётах (дольше — рискуем обрывом на транспорте);
- **не больше 2 повторов**, с паузой между ними;
- ⚠️ каждый повтор создаёт **новый** отчёт в очереди, а не забирает старый (коннектор генерирует новое имя отчёта на каждый вызов). Очередь Директа — 5 слотов, так что долбить бесполезно и вредно;
- два `processing` подряд → зафиксируй ограничение в находках и иди дальше на том, что собралось. Не выдумывай данные.

## Деньги: отчёты в рублях, настройки в микро

| Откуда | Единица | Что делать |
|---|---|---|
| Отчёты `report_*` (`Cost`, `AvgCpc`, `CostPerConversion`, `Revenue`) | **рубли** | ничего не делим: коннектор запрашивает отчёты с `returnMoneyInMicros: false` |
| Настройки `campaigns_get` (`WeeklySpendLimit`, `BidCeiling`, `AverageCpa`, `AverageCpc`, `DailyBudget.Amount`, `Value` в `PriorityGoals`) | **микро** | делить на 1 000 000: `AverageCpa 800000000` = 800 ₽ |
| Ставки `keywords_get` / `keywordbids_get` (`Bid`, `SearchBid`, `ContextBid`) | **микро** | делить на 1 000 000: `300000` = 0,30 ₽ |
| Запись (`campaigns_update`, `keywordbids_set`) — точечный режим и ведение | **микро** | рубли × 1 000 000; в превью показывай рубли |
| `Crr`, корректировки ставок | проценты | не деньги, не делим |

Перепутать единицы = ошибиться в миллион раз: «лимит 10 млрд ₽» в отчёте или ставка 300 000 ₽ при записи.

Анализаторы (`normalize_report.py`, `analyze_placements.py`, `run_analysis.py`) настроены на рубли по умолчанию — флаг денег им передавать не надо. Флаг `--money-in-micros` существует только для ручных выгрузок из интерфейса Директа, где деньги бывают в микро (1 000 000 = 1 ₽).

## ЕПК (UNIFIED_CAMPAIGN)

С конца 2024 Единая перформанс-кампания заменила отдельные ТГО/динамику/смарт-баннеры. По ЕПК часть срезов на уровне критериев беднее (для кампаний, собранных Мастером, `CriteriaId`/имя могут не отдаваться). Детекть `Type = UNIFIED_CAMPAIGN` и анализируй как смешанное размещение Поиск+Сеть+товарные; не жди от неё той же гранулярности, что от классического Поиска.

## Бюджет квот (units / баллы)

- Ошибочный вызов метода стоит ~20 баллов — не долби API в цикле при ошибках.
- Reports: не более 20 запросов к сервису за 10 секунд, не более 5 офлайн-отчётов в очереди; статистика — за последние 3 года.
- Типичный аудит (campaigns_get + report_campaign + search_queries + 2-3 CUSTOM_REPORT + bidmodifiers_get) укладывается в сотни-тысячи баллов. Не перезапрашивай то, что уже в артефактах за тот же период.

## Метрика

Метрика подключается **отдельным MCP-коннектором** (тулы с суффиксом `yandex_metrika_*`, префикс задаёт пользователь). Старый скриптовый слой из `parked/` больше не нужен. Тулы, рецепты M1–M7 и правила — `references/metrika-tools-map.md`.

Без коннектора Метрики аудит идёт по полям Директа: `BounceRate`, `AvgPageviews`, `Bounces`, `Sessions` приходят прямо в отчётах (Директ берёт их из привязанного счётчика). Недоступны только время на сайте, список целей, посадочные и потеря кликов. Правила по конверсиям — `references/attribution.md`.

## Ошибки и фолбеки

- **«Кабинет не указан, а у токена их несколько»** — передай `client_login` (список — `accounts_get`), запиши его в `_state.json`.
- **«Логин не найден или неактивен»** — кабинет из `accounts_get` мёртвый (отключён в Click.ru); исключи его и скажи маркетологу одной строкой.
- **`8000 — SelectionCriteria cannot contain an array`** — в отчёте не передан ни один фильтр. Добавь `Impressions > 0` и повтори. Фильтр нужен в каждом `report_*`.
- **Ответ `campaigns_get` не влез в контекст** — запроси без архива (`states: ["ON","OFF","SUSPENDED"]`), архивные — точечно по `ids`.

- **Тулов Директа нет в сессии** — коннектор не подключён. Процитируй блок «Как подключить коннектор» и остановись.
- **Ошибка авторизации / `isError: true`** — протух или неверен токен Click.ru в адресе коннектора.
- **Пустой `campaigns_get`** — кабинет пуст или в адресе не тот логин; уточни у маркетолога.
- **`status: processing` дважды** — см. правило офлайн-очереди выше: фиксируй ограничение, продолжай на собранном.
- **Отчёт вернул ошибку по полю** — убери проблемное поле и повтори один раз. Список полей: `yandex.com/dev/direct/doc/ru/reports/fields-list`.
- **Поля конверсий пусты везде** — нет связки счётчика по всему аккаунту; это находка №1, не баг. См. `references/attribution.md`.
- **Сезонность/мало данных** — расширь период или явно помечай выводы как «гипотеза».
