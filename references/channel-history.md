# История каналов — артефакт «что реклама клиента дала до нас»

**Когда читать:** Шаг 0 (поиск готовой истории), Цикл 0 ведения (сборка `strategy.md`),
быстрый выход «выгрузи историю каналов» и любой момент, когда история нужна, а её нет.

**История каналов** — короткая сводка о том, что прошлая реклама клиента реально дала: сколько
потрачено, сколько пришло лидов и по какой цене — по каждому каналу (Директ, VK Ads, Telegram
Ads, посевы…) и внутри Директа по типам кампаний (Поиск, РСЯ, ЕПК, ретаргет). Каждая строка —
с выводом и числами, на которых вывод построен.

## Путь клиента и место аудита в нём

Обычный порядок такой: **стратегия** (`marketing-strategist`) → **запуск** (`yandex-direct-manager`) →
**этот скилл** (аудит, точечные правки, ведение). Поэтому к моменту, когда включают аудит,
история обычно **уже есть** — её собирал стратег на входе стратегии. Аудит её **находит и
использует**, а собирает заново, только если её нет или нужна свежая за другой период. Тогда
аудит — производитель файла: у него есть данные кабинета и Метрики.

## Как называется и где лежит

Имя всегда одно: **`channel_history.md`** (для человека) + **`channel_history.json`** (для
скилла), поля одинаковые. Менеджер хранит нормализованную копию под именем
`_channel_history.md` — с подчёркиванием, как все его служебные файлы.

**Где искать готовую историю** — по порядку, первое найденное и берём:

| # | Где | Кто положил |
|---|---|---|
| 1 | Приложено в чате | маркетолог |
| 2 | `<project_dir>/lead/<slug>/channel_history.json` / `.md` | этот скилл, Цикл 0 ведения |
| 3 | `<project_dir>/marketing-campaigns/<slug>/channel_history.json` / `.md` | `marketing-strategist` |
| 4 | `<project_dir>/direct-campaigns/<slug>/_channel_history.md` (раздел «Каналы») | `yandex-direct-manager` |
| 5 | `direct-audits/<slug>/channel_history.json` / `.md` | этот скилл, прошлый аудит в той же сессии |

Ничего не нашлось — спроси одной строкой: «Есть файл истории каналов от стратегии или запуска?
Приложите `channel_history.md`. Нет — соберу историю Директа из кабинета сам или пойдём без
истории».

⚠️ **Claude Desktop:** файлы одного чата в другом не видны, а папки проекта может не быть.
Если стратегию и запуск делали в других чатах — файл нужно приложить.

**Куда класть свою историю:** в ведении — `lead/<slug>/channel_history.md` + `.json` (рядом со
`strategy.md`, переживает сессии); в аудите и точечном режиме — `direct-audits/<slug>/`.

## Контракт файла

> ⚠️ **Этот раздел — общий для трёх скиллов:** `yandex-direct-audit` (этот — производитель
> файла), `marketing-strategist` (использует историю при выборе каналов и передаёт дальше) и
> `yandex-direct-manager` (использует при запуске). Скиллы ставятся отдельными пакетами и не
> читают файлы друг друга, поэтому контракт продублирован. Меняешь поля — меняй во всех трёх.

Файл — `channel_history.md` (для человека) и/или `channel_history.json` (для скилла), поля
одинаковые.

**Шапка — условия, на которых построены выводы.** Без шапки строкам верить нельзя:

| Поле | Что внутри | Пример |
|---|---|---|
| `site` | сайт / продукт | `example.ru` |
| `period` | период, **выбранный пользователем** | `2026-04-01..2026-09-30` |
| `lead_definition` | что считали лидом: id и названия целей + как выбраны | `[123, 456] «Заявка», «Звонок» — ключевые цели стратегий кампаний` |
| `thresholds` | пороги выводов, **с которыми** построена таблица | `min_clicks: 30, min_days: 14, target_cpa: 3000, expensive_ratio: 1.5` |
| `created_by` | кто и когда собрал | `yandex-direct-audit 2026-10-06` / `со слов клиента` |

**Строки — по одной на канал или тип кампании:**

| Поле | Что внутри | Пример |
|---|---|---|
| `channel` | канал | `yandex_direct`, `vk_ads`, `telegram_ads`, `other` |
| `campaign_type` | тип внутри канала (для Директа обязателен) | `search`, `rsya`, `unified`, `retargeting`, `—` |
| `account` | кабинет / аккаунт | логин кабинета Директа |
| `status` | `ran` — крутилась, `never_ran` — черновик / не запускали, `archived` — в архиве | `ran` |
| `spend` | расход за период, ₽ (без НДС — как в отчётах Директа) | `240000` |
| `clicks` | клики | `3100` |
| `leads` | лиды по `lead_definition` | `96` |
| `cpa` | `spend / leads`; при `leads = 0` — `null` | `2500` |
| `counter_id`, `link` | счётчик и состояние связки Директ↔Метрика (`green` / `yellow` / `red`, см. Шаг 0.5.2) | `12345678`, `green` |
| `source` | откуда цифры | `direct` / `metrika` / `client` |
| `verdict` | вывод (ниже) | `no_leads` |
| `verdict_reason` | **одна строка с числами и порогом**, по которым сделан вывод | `0 лидов при 410 кликах и 62 днях показов (порог «мало данных»: <30 кликов или <14 дней)` |
| `note` | всё остальное, в т.ч. причина, почему не запускали | `не прошла модерацию — медицинская тематика без лицензии` |

**Выводы (`verdict`)** — считаются по порогам из шапки:

| Вывод | Условие по умолчанию |
|---|---|
| `no_data` — мало данных | `clicks < 30` **или** показов меньше 14 дней |
| `no_leads` — не дал лидов | данных достаточно, `leads = 0` |
| `expensive` — дорого | `cpa > target_cpa × 1.5`. Нет `target_cpa` — вывод не ставится, только CPA |
| `works` — работает | данных достаточно, лиды есть, не дорого |
| `never_ran` — не запускали | `status = never_ran`; вывода о канале нет, есть причина в `note` |

**Пороги — не догма.** У бизнеса бывают свои представления о «мало данных» и «дорого» (длинный
цикл сделки, дорогой чек). Поэтому пороги всегда пишутся в шапку, а каждый вывод — с
`verdict_reason`: человек видит, на каких числах построен вывод, и может их поправить.

Пример `channel_history.json`:

```json
{
  "site": "example.ru",
  "period": "2026-04-01..2026-09-30",
  "lead_definition": {"goal_ids": [123, 456], "names": ["Заявка", "Звонок"],
                      "how": "ключевые цели стратегий кампаний"},
  "thresholds": {"min_clicks": 30, "min_days": 14, "target_cpa": 3000, "expensive_ratio": 1.5},
  "created_by": "yandex-direct-audit 2026-10-06",
  "rows": [
    {"channel": "yandex_direct", "campaign_type": "search", "account": "login-1", "status": "ran",
     "spend": 240000, "clicks": 3100, "leads": 96, "cpa": 2500, "counter_id": 12345678,
     "link": "green", "source": "direct", "verdict": "works",
     "verdict_reason": "CPA 2500 ≤ 3000 × 1.5 при 96 лидах", "note": ""},
    {"channel": "yandex_direct", "campaign_type": "rsya", "account": "login-1", "status": "ran",
     "spend": 80000, "clicks": 410, "leads": 0, "cpa": null, "counter_id": 12345678,
     "link": "green", "source": "direct", "verdict": "no_leads",
     "verdict_reason": "0 лидов при 410 кликах и 62 днях показов", "note": ""},
    {"channel": "vk_ads", "campaign_type": "—", "account": "", "status": "ran",
     "spend": 50000, "clicks": null, "leads": 0, "cpa": null, "counter_id": null,
     "link": null, "source": "client", "verdict": "no_leads",
     "verdict_reason": "со слов клиента: 50 тыс. за 2 месяца, ни одной заявки", "note": ""}
  ]
}
```

## Чем отличается от `baseline.json`

Оба файла — «как было», но про разное и для разного:

| | `channel_history` | `baseline.json` |
|---|---|---|
| О чём | что реклама дала **до** нас: до стратегии, запуска, ведения | метрики кампаний **в момент старта** ведения |
| Охват | все каналы клиента: Директ по типам кампаний + VK, Telegram, посевы… | только кампании Директа под ведением (+ поведение из Метрики) |
| Выводы | у каждой строки вывод (`works`, `no_leads`…) с числами и порогом | выводов нет, только числа |
| Кто делает | стратег, этот скилл или клиент словами | этот скилл, Цикл 0 |
| Зачем | решать, **какие** каналы и типы кампаний вообще стоит крутить, и не повторять провалы | мерить прогресс: «стало ли лучше, чем было, когда начали вести» |
| Меняется | только заменой на новую выгрузку за новый период | никогда |

Коротко: история отвечает на вопрос «что вообще работает у этого клиента», baseline — на вопрос
«лучше ли стало при нас». Не подменяй одно другим: baseline не знает, что VK уже провалился, а
история не знает, какой был CPA в день старта ведения.

## Как `strategy.md` использует историю (ведение)

В Цикле 0 история становится частью стратегии — блоком `history` во фронтматтере
`strategy.md` (схема — `lead-strategy.md`):

```yaml
history:
  channel_history: file | client | none   # откуда история; none — истории нет
  file: lead/<slug>/channel_history.json   # путь к файлу или null
  period: 2026-04-01..2026-09-30
  lead_definition: "цели 123, 456 — ключевые цели стратегий"
  works_types: [search]                   # работало — ориентир
  weak_types: [rsya]                      # no_leads / expensive при достаточных данных
  history_cpa: {search: 2500}             # фактический CPA по истории, ₽
```

Что с этим делает ведение:
- **Цикл 0:** `target_cpa` сверяется с `history_cpa`. Таргет в 3 раза ниже факта — скажи прямо
  до подтверждения стратегии.
- **Фаза C (план правок):** правка, которая **наращивает** тип из `weak_types` (бюджет, ставки,
  новые группы), — рекомендация с цифрами из истории, а не действие, как для `protected`.
  Сокращать и чистить слабый тип можно по обычным правилам.
- **Фаза D (отчёт):** если находка касается типа из `weak_types` — одной строкой контекст: «РСЯ
  и раньше не давала лидов: 0 при 410 кликах за 62 дня».
- Цикл историю **не переписывает**. Новая история — только новой выгрузкой за новый период,
  с подтверждением человека; старый файл сохрани с датой в имени.

## Что делать, если истории нет

1. **Предложи собрать историю Директа из кабинета** — у аудита для этого всё есть (рецепт ниже).
   Остальные каналы — со слов клиента или из Метрики по источникам.
2. Маркетолог отказался или рекламы не было → `channel_history: none` в `_state.json` и в
   `strategy.md`. Дальше:
   - в отчёте аудита и в ведении — пометка **«без истории»** там, где вывод зависел бы от
     прошлого опыта (например, «масштабировать РСЯ»);
   - `weak_types` пустой — ограничений по типам нет, только обычные guardrails;
   - `baseline.json` всё равно снимается: он от истории не зависит.

## Как аудит собирает историю (производитель)

Запускается быстрым выходом «выгрузи историю каналов», по предложению в Цикле 0 или в конце
аудита («выгрузить историю каналов для стратегии?»). Read-only.

1. **Кабинет и кампании** — как в Шаге 0: только явным выбором.
2. **Период — всегда спроси** (по умолчанию его не выбираем: 3, 6 или 12 месяцев — решает человек).
3. **Что считать лидом — с вариантами:** 1) ключевые цели стратегий кампаний (`PriorityGoals`) —
   **по умолчанию**; 2) все живые конверсионные цели счётчика (`goals_get`, рецепт M1);
   3) конкретные цели, которые назовёт маркетолог. Записывается в `lead_definition`.
4. **Пороги** — по умолчанию `min_clicks: 30`, `min_days: 14`, `expensive_ratio: 1.5`,
   `target_cpa` — KPI из скоупа (нет — вывод `expensive` не ставится). Покажи и дай поправить:
   у бизнеса свои представления о «мало данных» и «дорого».
5. **Директ по типам кампаний.** Тип — из `01_account_map.json`: только Поиск → `search`, только
   Сеть → `rsya`, ЕПК с обеими сторонами → `unified`. Отчёт `report_campaign` за период по
   выбранным целям и атрибуции, поля `CampaignId`, `Date`, `Impressions`, `Clicks`, `Cost`,
   `Conversions` (фильтр `Impressions > 0` обязателен) → сумма по типу; дни с показами — число
   разных `Date`. Деньги из отчёта — уже в рублях.
6. **Черновики.** Кампании без единого показа за всё время (`campaigns_get` → `Statistics.Impressions = 0`)
   — строка со `status: never_ran`; спроси, почему их не запустили (модерация / бюджет / передумали),
   ответ — в `note`. Вывода «тип не работает» по ним нет.
7. **Другие каналы** — при `metrika_ok` рецепт **M7** (`metrika-tools-map.md`): визиты и
   достижения целей по рекламным системам и UTM-меткам. Расходов там нет — спроси у
   маркетолога; не знает — `spend: null`, вывод только по лидам (`expensive` не ставится).
   Без Метрики — со слов клиента, `source: client`.
8. **Вывод по каждой строке** — по порогам из шапки, с `verdict_reason` (числа + порог).
9. Запиши `channel_history.md` + `channel_history.json` по контракту и покажи сводку: «Вот что
   дала реклама за период. Файл можно приложить к стратегии или к запуску».
