# Интеграция Яндекс.Метрики в аудит

Direct-only MCP отвечает на вопрос «сколько потрачено и сколько кликов», но не на «что эти люди делали на сайте и где правда про конверсии». Метрика закрывает этот пробел и делает выводы аудита точными. Доступ — через `scripts/metrika_api.py` (read-only, OAuth-токен в окружении). Этот reference объясняет, что и зачем тянуть и как класть данные Метрики на сущности Директа.

## Зачем это нужно (что меняется в выводах)

- **Правда про конверсии и атрибуцию.** Direct считает конверсии по своей логике и привязанным целям. Метрика даёт полную воронку и показывает, как меняется картина между моделями (`first` / `last` / `lastsign` / последний клик Директа). Кампания, «убыточная» по последнему клику, может быть верхом воронки — её нельзя резать. Без этого среза рекомендации «срезать» рискованны.
- **Поведение по площадкам РСЯ.** Отказы, глубина и время на сайт по каждой площадке (аналог отчёта Метрики «Директ, площадки»). Это и есть надёжная чистка площадок — не «по нулю конверсий вслепую», а «площадка X: 80% отказов, 12 сек на сайте → мусор».
- **Поведение поисковых запросов.** Отказ/глубина по запросу. Запрос с расходом и нулём конверсий, но низким отказом и хорошей глубиной — кандидат НЕ в минус (конвертит с задержкой), а на доработку посадочной.
- **Поведение сегментов** (устройство/гео/пол-возраст) на уровне сайта, а не только клика. Корректировки ставок становятся обоснованными поведением, а не только CPA клика.

## Доступ и авторизация

`scripts/metrika_api.py` берёт OAuth-токен из `YANDEX_METRIKA_TOKEN` (или `YANDEX_DIRECT_TOKEN`, если токен общий и имеет скоуп `metrika:read`). Только чтение: Reporting API (`stat/v1/data`) и список целей (Management API). Ничего не меняет.

Если регион под сетевыми ограничениями — задай `HTTPS_PROXY`, `urllib` подхватит.

## Мост Direct ↔ Метрика

Данные Метрики ложатся на сущности Директа через Direct-срезы с префиксом модели атрибуции (вместо `<attr>` подставляется `lastsign`/`last`/`first`):

| Сущность Директа | Срез Метрики |
|---|---|
| Кампания | `ym:s:<attr>DirectClickOrderName` (и `...DirectClickOrder` — id) |
| Группа объявлений | `ym:s:<attr>DirectBannerGroup` |
| Объявление | `ym:s:<attr>DirectClickBanner` |
| Условие показа / фраза | `ym:s:<attr>DirectPhraseOrCond` |
| Площадка | `ym:s:<attr>DirectPlatform` |
| Поиск vs Сеть | `ym:s:<attr>DirectPlatformType` (`'search'` / `'context'`) |

Чтобы ограничить выборку только трафиком Директа — фильтр `ym:s:<attr>TrafficSource=='ad'`.

⚠️ Имена чувствительны к регистру и со временем менялись. `DirectSearchPhrase` и `directBanner` — устаревшие/неверные; используй `DirectPhraseOrCond` и `DirectClickBanner`. При ошибке по полю сверяйся с живым списком: `yandex.com/dev/metrika/ru/data/dimensions`.

## Пресеты скрипта (по шагам аудита)

| Команда | Что даёт | Шаг |
|---|---|---|
| `--preset goals` | список целей счётчика (id, имя, тип) — какие цели вообще есть | 1-2 |
| `--preset attribution --goal <id>` | конверсии по кампаниям; запусти с разными `--attribution` и сопоставь модели | 2 |
| `--preset queries` | отказ/глубина/время по условиям-фразам Директа | 3 |
| `--preset placements` | отказ/глубина/время по площадкам РСЯ | 4 |
| `--preset segments --segment device\|gender\|age\|geo` | поведение по сегменту, только Direct-трафик | 5 |

Произвольный запрос — через `--metrics` + `--dimensions` (+ `--filters`). `--dry-run` показывает запрос без вызова API.

## Ключевые метрики Метрики

`ym:s:visits`, `ym:s:bounceRate` (% отказов), `ym:s:pageDepth` (глубина), `ym:s:avgVisitDurationSeconds` (время на сайте), `ym:s:goal<id>reaches` (достижения цели), `ym:s:goal<id>conversionRate` (CR по цели), `ym:s:sumGoalReachesAny` (любые цели).

Определение отказа в Метрике: визит < 15 секунд, одна страница, без целевых действий. Пороги — в `audit-thresholds.md`: поиск до ~30% норма, РСЯ допустимо выше; оценивать в связке с конверсиями.

## Атрибуция — зафиксировать одну

Дефолт Метрики сменился на `lastsign` (последний значимый переход). **Зафиксируй одну модель на весь аудит** и указывай её рядом с каждым конверсионным числом; не сравнивай числа из разных моделей как одно. Для оценки вклада Директа полезно прогнать `attribution`-пресет дважды (`--attribution lastsign` и `--attribution last_direct`) и показать разницу — это часто и есть аргумент «не режьте эту кампанию».

## Как класть на данные Директа

1. Из Шага 1 у тебя есть карта «кампания → CounterIds». Бери счётчик из неё (обычно один на проект; если у кампаний разные — гоняй скрипт по каждому).
2. Тяни Метрику тем же периодом, что и Direct-отчёты.
3. Джойни по имени сущности: `DirectClickOrderName` ↔ имя кампании из Директа; `DirectPlatform` ↔ `Placement` из CUSTOM_REPORT; `DirectPhraseOrCond` ↔ запрос/условие.
4. В находку клади обе стороны: расход/клики/конверсии из Директа + отказ/глубина/реальные цели из Метрики. Пример: «Площадка X — расход 12 400 ₽, 0 конверсий (Direct) + отказы 81%, 9 сек (Метрика) → отключить, уверенность высокая».

## Ограничения и честность

- **Нет связки счётчика с кампанией** → срез по этой кампании в Метрике не соберётся через Direct-фильтр; помечай «поведение не оценено». Это находка high (без целей нет оптимизации).
- **Семплирование.** На больших объёмах Метрика семплирует; скрипт просит `accuracy=full`, но при огромном трафике данные приблизительны — отметь, если `total_rows` подозрительно мал.
- **Лимиты:** ~30 запросов/сек к API, до 5000/день на логин (сброс 00:00 GMT), HTTP 429/420 при превышении — не долби в цикле.
- **Расхождение Direct vs Метрика — норма**, а не ошибка: разные модели атрибуции, дедупликация, кросс-девайс. Не «сводить копейка в копейку», а объяснять расхождение моделью атрибуции.
- Глубокий per-hit анализ (Logs API) — вне скоупа этого скрипта; если понадобится сырьё на уровне визитов, это отдельная задача.
