# Ведение: стратегия проекта, состояние и недельный такт

Этот reference работает **только в режиме ведения** (см. mode-gate в `SKILL.md`). Он отвечает на три вопроса: где живёт память проекта между запусками, откуда берётся файл стратегии и как понять — это новый недельный цикл или дозапуск прерванного.

Аудит — разовая read-only диагностика. Ведение — та же диагностика, обёрнутая в **повторяющийся недельный цикл** с целью (с чем сравнивать) и записью правок. Диагностический движок (Шаги 1–6 аудита) переиспользуется как фаза «диагноз» внутри цикла. Здесь — только то, что аудиту не нужно.

---

## Дом состояния — папка на диске пользователя

В режиме ведения **нельзя** держать состояние в рабочей папке сессии: облачная сессия эфемерна, а человек запускает ведение раз в неделю, часто в новой сессии. Через неделю новая сессия должна найти историю и цели — значит, они лежат на диске пользователя, а не в контексте.

**Первый запуск ведения:** попроси пользователя подключить папку проекта (в Claude Desktop — кнопка «Add folder») или назвать путь к ней. Это явное согласие, а не молчаливый захват. Запиши путь в `_state.json` (`project_dir`) — на следующих запусках переиспользуй, повторно не спрашивай.

Если подключить папку в этой среде нельзя (нет доступа к файловой системе пользователя) — предупреди прямо: без постоянной папки ведение выродится в разовый аудит, потому что память между неделями хранить негде. Предложи разовый аудит вместо ведения.

### Структура папки

```
<project_dir>/lead/<slug>/
  strategy.md            — «конституция»: цели, KPI-таргеты, guardrails, что не трогать
  baseline.json          — метрики на старте ведения (мерить прогресс, а не только неделя-к-неделе)
  _state.json            — project_dir, slug, client_login, kpi, атрибуция, current_cycle, статус коннектора
  changes_log.jsonl      — append-only журнал ВСЕХ правок, залитых в аккаунт (ведёт scripts/changes_log.py)
  cycles/
    2026-08-28/          — папка недельного цикла
      diagnosis.json     — находки фазы диагноза (тот же формат, что findings аудита)
      proposed.json      — предложенные правки цикла (с тегом обратимости и guardrail-проверкой)
      applied.json       — что реально применено после гейта (ссылки на строки changes_log)
      cycle_report.md    — сводка недели для человека
```

`slug` — короткое имя проекта; при нескольких кампаниях у одного клиента веди по одному `slug` на кабинет, кампании разделяй внутри.

## `strategy.md` — конституция проекта

Это живой документ, с которым сверяется каждый недельный цикл. Каждая правка в аккаунте должна быть объяснима как «приближает к цели из strategy.md и не нарушает guardrails». Схема (YAML-фронтматтер + человеческие заметки):

```yaml
---
slug: <slug>
client_login: <логин кабинета>
created: <дата старта ведения>
source: file | manager | interview   # откуда собрана стратегия (см. ниже)

# Цели — с чем сравнивает каждый цикл
goals:
  primary_kpi: cpa | drr | cpl        # главная метрика
  target_cpa: <₽ или null>
  target_drr: <% или null>
  target_cpl: <₽ или null>
  monthly_budget_cap: <₽>             # потолок расхода в месяц
  goal_ids: [<goal_id Метрики>]        # что считаем конверсией
  attribution_default: LSCCD

# Что НЕЛЬЗЯ трогать автоматически (уходит в рекомендации, не в действия)
protected:
  campaigns: [<id или имена бренд/имиджевых РК>]
  note: <например: бренд-кампанию не оптимизировать по CPA — это верх воронки>

# Guardrails — пределы одной правки за цикл (пороги пишет человек на старте)
guardrails:
  max_bid_change_pct: 20              # ставку/корректировку не менять больше чем на X% за цикл
  max_placements_off_per_cycle: 30   # не отключать больше N площадок разом
  max_budget_change_pct: 20          # бюджет не менять больше чем на X% за цикл (триггер сброса обучения — 20%)
  min_clicks_for_action: 30          # ниже — «мало данных, не трогать»
  require_confirm_for_destructive: true  # удаление/пауза кампаний — всегда отдельный конфирм

# Контекст, влияющий на выводы
context:
  seasonality: <например: пик в декабре, спад в июле>
  calltracking: on | off
  notes: <любые ограничения проекта словами>
---

# Заметки по проекту
<свободный текст: что уже пробовали, гипотезы, договорённости с клиентом>
```

Guardrails — сердце безопасности ведения. Всё, что за их пределом, скилл **не применяет сам**, а выносит рекомендацией на ручное действие, даже если по метрикам «надо». Пороги задаёт человек в Цикле 0; дефолты выше — разумная отправная точка.

## Откуда берётся стратегия — Цикл 0 (инициализация)

Стратегия не появляется сама. Её собирает **разовый bootstrap** при первом включении ведения. Три источника, по приоритету — бери первый подходящий:

### Источник 1 — у человека уже есть файл стратегии
Спроси, есть ли документ со стратегией/медиапланом/целями. Есть — прочитай его и **нормализуй** в схему `strategy.md` выше. Не переспрашивай то, что уже написано; интервью только по недостающим полям (обычно это `target_cpa`/`target_drr`, `monthly_budget_cap`, `guardrails`). Помечай `source: file`.

### Источник 2 — кампанию делали скиллом yandex-direct-manager
Если в `project_dir` (или в подсказанной пользователем папке) есть `direct-campaigns/<slug>/` с артефактами manager — **выведи стратегию автоматически**:
- цели и УТП → из `00_brief.md`;
- `target_cpa` / бюджет / коллтрекинг → из `00_brief.md` + `09_bidding_strategy.json`;
- `goal_ids`, `counter_id` → из `07_metrika_goals.json`;
- структура и защищённые РК → из `05_campaign_structure.json`.

Покажи собранный черновик на подтверждение. Помечай `source: manager`. Это штатная стыковка: выход creation-скилла = вход ведения без единого лишнего вопроса.

### Источник 3 — ничего нет (кампанию вели руками)
Проведи короткое **интервью по целям** (главный KPI, целевой CPA/ДРР, потолок бюджета, цели Метрики, что не трогать, сезонность), затем прогони **первый диагноз как baseline** и предложи черновик стратегии на его основе. Помечай `source: interview`.

### После bootstrap
Запиши `strategy.md` + `baseline.json` (снимок метрик на старте) + `_state.json`. Baseline — точка отсчёта: без него виден только тренд неделя-к-неделе, но не «стало ли лучше, чем было до нас».

## Возобновление и недельный такт

Всё нужное для продолжения — на диске. На **любом** запуске (та же сессия или новая) ведение восстанавливается одинаково:

1. Найди `<project_dir>/lead/*/` → прочитай `_state.json`, `strategy.md`, последний цикл в `cycles/`.
2. Определи, что делать:
   - **последний цикл не закрыт** (нет `applied.json`) → дозапуск: продолжай с прерванного места, отчёты за тот же период не перезапрашивай;
   - **последний цикл закрыт ≥ 7 дней назад** → новый недельный цикл;
   - **закрыт < 7 дней назад** → спроси: «Прошлый цикл был N дней назад, для стратегий рано (обучение сбрасывается от частых правок). Всё равно прогнать?»;
   - **папки нет вообще** → это первый запуск → Цикл 0 (bootstrap выше).

Не начинай с нуля, если папка есть. Частые правки — враг автостратегий: смена бюджета >20%, смена цели/атрибуции сбрасывают обучение (`optimization-playbook.md` → «Автостратегии»). Недельный такт — не каприз, а защита обучения; ежедневных прогонов избегай, кроме первой недели новой кампании и явной аварии (резкий слив).

---

## Что цикл кладёт обратно в папку

Каждый недельный цикл дописывает: `cycles/<дата>/` (диагноз, предложенное, применённое, сводка), строки в `changes_log.jsonl` (по одной на каждую залитую правку — ведёт `scripts/changes_log.py`), и при изменении целей — обновляет `strategy.md`. Baseline не трогается никогда — это фиксированная точка отсчёта.
