# Запаркованный слой Метрики

Здесь лежит рабочий, ничем не сломанный код интеграции с Яндекс.Метрикой. Он **выведен из скилла**, а не удалён.

## Почему запарковано

Скилл собран под **Claude Desktop**. Там skills исполняются в песочнице code execution, у которой **нет исходящей сети**. `metrika_api.py` ходит на `https://api-metrika.yandex.net` и на первом же вызове падает `SystemExit("Сеть недоступна…")`. Хуже того, вызов стоял в предполётной проверке Шага 0 — то есть аудит спотыкался на самом старте, и модель могла прочитать это как «аудит невозможен».

MCP-коннекторы этого ограничения не имеют: их вызывает хост-приложение, а не песочница. Поэтому правильное решение — не скрипт, а **Метрика-MCP**.

## Что лежит

| Файл | Что это |
|---|---|
| `metrika_api.py` | read-only клиент Reporting API + список целей. Пресеты `goals / attribution / placements / queries / segments`, `--dry-run`, `--show-attribution-map` |
| `metrika-integration.md` | методология: мост Direct↔Метрика (`ym:s:<attr>DirectClickOrderName` и др.), пресеты по шагам, семплирование, лимиты |

Скрипт — лист: его никто не импортирует, парковка ничего не ломает.

## Что скилл потерял

Почти всё поведение заменяется полями самих Direct-отчётов (`BounceRate`, `AvgPageviews`, `Bounces`, `Sessions`) — их Директ берёт из привязанного счётчика. Реально недоступны только два пункта:

1. **Время на сайте** — у Директа такого поля нет вообще. Формулировки вида «отказы 81%, 9 сек» ушли из шаблонов отчёта.
2. **Автодискавери целей счётчика** — `goal_ids` теперь обязательный вопрос скоупа на Шаге 0.

Плюс: там, где Direct-отчёт молчит (ЕПК, часть срезов уровня критериев), второго источника больше нет — помечаем «без поведения».

Атрибуция **не парковалась**: от неё зависят конверсии в самих Direct-отчётах. Direct-половина словаря переехала в `references/attribution.md`.

## Как расконсервировать

Когда появится Метрика-MCP, вернуть надо не скрипт, а маршрут через тулы коннектора:

1. `references/attribution.md` — вернуть колонку с именами моделей Метрики (таблица в `metrika-integration.md`, раздел «Атрибуция»).
2. Шаг 0 — добавить четвёртым пунктом предполётки проверку Метрика-коннектора и сверку счётчика с `CounterIds`.
3. Шаг 1 — вернуть автодискавери целей и артефакт `_metrika_goals.json`; снять обязательность `goal_ids` в скоупе.
4. Шаги 3/4/5 — вернуть в субагенты блок «Шаг C. Обогащение поведением», заменив вызовы `metrika_api.py --preset X` на соответствующие тулы MCP. Мост и логика джойна — в `metrika-integration.md`, раздел «Как класть на данные Директа».
5. Вернуть время на сайте в `assets/findings_schema_example.json` и `references/report-template.md`.
6. `evals/evals.json` — вернуть кросс-чек атрибуции через Метрику как отдельный кейс (сейчас он сделан средствами Директа).

Шаг 2 расконсервировать **не нужно**: кросс-чек воронки теперь делается одним Direct-отчётом с `attribution_models: ["LSCCD","FC"]`, и это дешевле и точнее, чем два прогона Метрики с джойном по имени кампании.
