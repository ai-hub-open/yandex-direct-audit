# yandex-direct-audit

> Аудит и ведение работающих кампаний Яндекс Директа. Три режима в одном скилле.

Скилл работает с действующим кабинетом Директа в **трёх режимах** через **коннектор Яндекс Директа** (расход, структура, конверсии, поведение) и по желанию **коннектор Яндекс Метрики** (цели, время на сайте, посадочные, потеря кликов). Коннектор работает по MCP — это подключение агента к рекламной системе. Работает в Claude Desktop, Claude Code и claude.ai.

- **Режим аудита** (по умолчанию) — разовая **диагностика без изменений в кабинете**: от описи кампаний до HTML-отчёта с приоритетами — что отключить, что усилить, что исправить в каждой кампании.
- **Точечный режим** — «проверь кампанию и поправь»: выбранные кампании → диагноз по той же методике → предварительный список правок → запись после вашего «ОК», с журналом для отката. Без папки проекта и файла стратегии; пределы правок — по умолчанию.
- **Режим ведения** — повторяющийся **недельный цикл управления**: сверка с целью проекта (`strategy.md`) → диагноз по той же методике → проверка эффекта прошлых правок → изменения в кабинете после вашего подтверждения, с журналом (`changes_log.jsonl`) и откатом. Состояние хранится в папке на диске и сохраняется между сессиями.

Режим скилл выбирает сам по вашей просьбе — правило выбора записано в начале `SKILL.md`. Создание новой кампании с нуля — не задача этого скилла.

## С чего начать (навигация по пакету)

| Файл / папка | Зачем |
|---|---|
| `SKILL.md` | основная инструкция: выбор режима → 7-шаговый аудит (Шаги 0–7) и недельный цикл ведения (Цикл 0/N) |
| `subagents/` | инструкции для Шагов 3/4/5, которые выполняются в отдельном контексте (не отдельные скиллы) |
| `references/` | методология и пороги каждого шага; `lead-strategy.md` + `lead-write-safety.md` — режим ведения |
| `scripts/` | нормализация отчётов, анализаторы запросов и площадок, история каналов, сборка отчёта, сборка архива скилла |
| `parked/` | старый скриптовый слой Метрики (заменён коннектором Метрики, в архив не входит) |
| `assets/` | словарь мусорных имён площадок + образец `findings.json` |
| `evals/` | тест-кейсы скилла |

## Что делает — 7 шагов

0. Подключение коннектора, проверка доступов, параметры аудита (период, KPI, цели)
1. Инвентаризация и структурный аудит
2. Статистика по кампаниям (+ сверка воронки: две модели атрибуции в одном отчёте)
3. ⭐ Анализ поисковых запросов: минус-слова + действия по ключевым фразам (методика бывшего скилла phrase-minus) — **в отдельном контексте**, `search-queries`
4. ⭐ Чистка площадок РСЯ (методика бывшего скилла rsya-minus) — **в отдельном контексте**, `rsya-placements`
5. ⭐ Корректировки ставок (точки роста) — **в отдельном контексте**, `bid-segments`
6. Объявления и релевантность
7. Сборка финального HTML-отчёта (дашборд, печатается в PDF из браузера)

## Режим ведения — недельный цикл

Та же диагностика (Шаги 1–6), повторяемая каждую неделю с целью и записью правок. Полная логика — `SKILL.md` → «Режим ведения», методология — `references/lead-strategy.md` (где хранится состояние, схема `strategy.md`, 3 источника стратегии на старте, возобновление) и `references/lead-write-safety.md` (подтверждение правок, запись в журнал до изменения, проверка без записи, пределы правок, обратимые и необратимые правки, карта пишущих инструментов).

- **Цикл 0 (разово):** подключить папку проекта → собрать `strategy.md` (готовый файл стратегии / автоматически из материалов скиллов «Стратег» и «Запуск Директа» — вместе с историей каналов / интервью + снимок показателей на старте) → зафиксировать `baseline.json`.
- **Цикл N (еженедельно):** проверка эффекта прошлых правок (главная часть ведения) → диагноз относительно цели → план правок с проверкой пределов → ваше подтверждение → применение одобренного с записью в `changes_log` → закрытие цикла.

Состояние хранится на диске пользователя (`<project_dir>/lead/<slug>/`), а не в сессии, которая закрывается, — так ведение продолжается из недели в неделю и в новых сессиях. Скрипт `scripts/changes_log.py` ведёт журнал правок со значениями до и после и собирает план отката.

## Архитектура: оркестратор + субагенты

Оркестратор держит общую картину в основном контексте (параметры аудита, `_state.json`, точки контроля, сборка отчёта). Три тяжёлых шага сбора данных (поисковые запросы — Шаг 3, площадки РСЯ — Шаг 4, сегменты ставок — Шаг 5) вынесены в изолированные субагенты (`context: fork`): они собирают гигантские TSV-отчёты в своём контексте и возвращают наверх **только сводку ≤20 строк**. Это не даёт контексту оркестратора разрастись к моменту сборки отчёта. **Если форк недоступен** — шаги выполняются инлайн по тем же reference/scripts. Делегирование — оптимизация, а не жёсткая зависимость.

Пакет Claude Desktop должен содержать **ровно один `SKILL.md`**, поэтому субагенты — не отдельные скиллы, а **брифы** `subagents/<имя>.md`: оркестратор читает бриф и передаёт его форку как задачу вместе с аргументами. Бриф самодостаточен, методологию пересказывать не нужно.

Списком инструментов форки не ограничены — имя коннектора у каждого своё, и жёсткий `allowed-tools` оставил бы субагента вообще без Директа; **read-only держится инструкцией** в блоке «Read-only — жёстко» каждого брифа.

**Шаг 4 — это перенесённый внутрь аудита движок бывшего отдельного скилла `yandex-direct-rsya-minus`**: анализатор `analyze_placements.py` + словарь `placement_patterns.json` + правила `rsya-minus-rules.md`. Он отдаёт готовый к вставке `minus_list.txt` по кампаниям.

**Шаг 3 — это движок бывшего скилла `yandex-direct-phrase-minus`** (`search-query-miner`): `query_analyzer.py` + `run_analysis.py` + словарь `query_patterns.json` + правила `phrase-minus-rules.md`. За один запуск даёт минус-слова по запросам (минус-слова кампании + минус-фразы группы → `minus_keywords.txt`) и действия по ключевым фразам (ставки/статус → `03_phrase_actions.md`).

## Имена артефактов

Рабочая папка: `direct-audits/<slug>/`. `00_scope.md` · `_state.json` · `01_account_map.{md,json}` · `02_campaign_performance.{md,json}` · `03_negative_candidates.json` + `minus_keywords.txt` + `03_phrase_actions.md` · `04_placement_candidates.{md,json}` + `minus_list.txt` · `05_bid_modifier_opportunities.{md,json}` · `06_creative_findings.{md,json}` · `findings.json` → `АУДИТ_<slug>.html`.

## Принципы

- **Режим решает всё.** В аудите — только чтение: ни основная инструкция, ни шаги в отдельном контексте не пишут в кабинет. В ведении правки применяются после вашего подтверждения, с журналом и откатом, в пределах из `strategy.md`. Решение всегда за маркетологом; кампанию из паузы или черновика скилл сам не запускает ни в каком режиме.
- **Деньги: отчёты — в рублях с НДС, настройки — в микроединицах API.** НДС включён по умолчанию (`include_vat`), чтобы расход по площадкам и сегментам сходился с расходом по кампаниям. Отчёты коннектор отдаёт в рублях — их не делим. Настройки кампаний и ставки (`campaigns_get`, `keywordbids_get`: лимиты, CPA, ставки, ценность целей) — в микроединицах, делим на 1 000 000; при записи — наоборот.
- **Кабинет и кампании — только явным выбором.** Кабинет подтверждается всегда, даже если у токена он один; кампании выбирает маркетолог. Без ответа скилл останавливается.
- **История каналов — вход, а не догадка.** Обычный путь клиента: стратегия → запуск → этот скилл. Историю каналов (`channel_history.md` / `.json` — что реклама давала до аудита) скилл ищет в материалах «Стратега» и «Запуска Директа», в ведении кладёт в блок `history` файла `strategy.md` и не наращивает без «ОК» типы кампаний, которые уже не работали. Нет истории — собирает её из кабинета по запросу («выгрузи историю каналов») или работает с пометкой «без истории». Это не `baseline.json`: baseline — метрики в день старта ведения, история — опыт клиента до начала ведения (`references/channel-history.md`).
- **Оплата за конверсии — свои правила.** Клики бесплатны, поэтому пороги «расход без конверсий» не применяются; вместо них — цель оплаты, мусорные конверсии и цена конверсии против KPI (`references/audit-thresholds.md`).
- **Доказательство обязательно.** Каждая находка подкреплена числами, периодом, объёмом данных и порогом. Мало данных — «недостаточно данных», а не выдуманный вывод.
- **Поведение — из полей самого отчёта.** Отказы и глубина просмотра (`BounceRate`, `AvgPageviews`) приходят вместе с расходом, если к кампании привязан счётчик. Нет связки — честная пометка «без данных о поведении», а не догадки.

## Зависимости (для scripts)

Только стандартная библиотека Python 3 — ни pip-пакетов, ни браузера, ни сети. Это осознанное
ограничение: скрипты исполняются в песочнице Claude Desktop, где ничего этого нет.

## Коннекторы

Скиллу нужен коннектор **Яндекс Директа**; коннектор **Яндекс Метрики** — по желанию (цели, время
на сайте, посадочные, потеря кликов). Серверы работают на стороне click.ru: в Claude добавляется
только адрес.

1. **Токен click.ru.** Профиль [click.ru/userinfo.html](https://click.ru/userinfo.html) → поле
   **API Token** → скопировать или **Создать**. Токен выпускайте в том аккаунте click.ru, где
   подключены кабинеты Директа. «Пересоздать» — только при утечке: старые подключения перестанут
   работать.
2. **Адрес Директа** ([подробнее](https://help.click.ru/7738)):

   ```
   https://direct-mcp.aihub.click.ru/c/<токен click.ru>
   ```

   - `…/c/<токен click.ru>/<кабинет>` — закрепить один кабинет: логин Директа, название или ID
     в click.ru (`@` → `%40`, пробел → `%20`).
   - `…/y/<OAuth-токен Яндекса>` — кабинет, созданный напрямую в Яндексе, без click.ru.

   Старая форма `/c/<логин>/<токен>/<ID пользователя>` ещё принимается сервером, но для новых
   подключений не используется.
3. **Адрес Метрики** (по желанию):

   ```
   https://metrika-mcp.aihub.click.ru/c/<токен click.ru>
   ```

   `…/c/<токен click.ru>/<аккаунт>` — один аккаунт; `…/y/<OAuth-токен Яндекса>` — напрямую
   в Яндекс. Для форм с `/c/` в click.ru должна быть подключена интеграция Метрики.
4. **Добавить в Claude.**
   - Claude Desktop / claude.ai: **Settings → Connectors → Add custom connector** → любое имя →
     адрес → **Continue** → **Add**, затем перезапустить Claude Desktop.
   - Claude Code: `claude mcp add --scope user --transport http yandex-direct "<адрес коннектора>"`.
5. **Проверка:** в сессии появились инструменты `yandex_direct_*`; попросите «покажи мои кабинеты».

⚠️ **Адрес коннектора равносилен паролю:** токен в нём открывает Директ, Вордстат, Метрику и VK
Рекламу этого аккаунта click.ru. Не пересылайте его; при утечке пересоздайте токен в профиле
click.ru.

## Установка скилла

Скилл ставится из каталога плагинов [claude-plugins](https://github.com/ai-hub-open/claude-plugins) —
там же выбор способа установки ([какой способ выбрать](https://github.com/ai-hub-open/claude-plugins#какой-способ-установки-выбрать))
и включение автообновления.

**Claude Desktop — через интерфейс.** Нужен Git
([как поставить](https://github.com/ai-hub-open/claude-plugins#шаг-1-установите-git)); после его
установки перезапустите Claude Desktop. **Settings → Plugins** →
**+ → Add marketplace → Add from repository** → `https://github.com/ai-hub-open/claude-plugins` → в
каталоге **ai-hub-open** нажмите **Add** у `yandex-direct-audit`. Автообновление — переключатель
**Auto-update** у каталога там же, в **Settings → Plugins**
([по шагам](https://github.com/ai-hub-open/claude-plugins#установка-в-claude-desktop)).

**Claude Code — командами:**

```
/plugin marketplace add ai-hub-open/claude-plugins
/plugin install yandex-direct-audit@ai-hub-open
```

Автообновление включается один раз: `/plugin` → **Marketplaces** → `ai-hub-open` →
**Enable auto-update**.

Дальше скажите «сделай аудит Директа» — он подключится сам, или
вызовите `/yandex-direct-audit:yandex-direct-audit`.

**Архивом (claude.ai, любой тариф).** На [странице релизов](https://github.com/ai-hub-open/yandex-direct-audit/releases)
в блоке **Assets** верхнего релиза скачайте `yandex-direct-audit.zip` (не «Source code») или
соберите сами: `python scripts/make_bundle.py`. Включите **Settings → Capabilities → Code execution
and file creation** и загрузите архив в **Customize → Skills → + → Create skill → Upload a skill**. Архив не включает `.env`, `docs/`, `parked/` и рабочие папки аудитов.

Рабочие папки `direct-audits/` и `lead/` создаются в текущей папке, а не внутри плагина: папка
плагина при обновлении заменяется целиком. Если раньше скилл лежал папкой в `~/.claude/skills/`,
удалите её, иначе скилл будет загружаться дважды.
