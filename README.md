# yandex-direct-audit

> Внутренний инструмент команды. Read-only аудит и поиск точек роста в работающих кампаниях Яндекс.Директа.

Скилл проводит маркетолога через **диагностику работающего аккаунта** Директа — от инвентаризации до приоритизированного PDF-отчёта «срезать слив / масштабировать / починить». Опирается на два источника: **Direct MCP** (расход/клики/структура) и **Яндекс.Метрику** (поведение и правда про конверсии). **Ничего не пишет в аккаунт** — каждое изменение подаётся как рекомендация на ручное подтверждение.

## С чего начать (навигация по пакету)

| Файл / папка | Зачем |
|---|---|
| `SKILL.md` | сам оркестратор — 7-шаговый workflow, читать для понимания/доработки логики |
| `subagents/` | форк-субагенты Шагов 3/4/5 (`context: fork`) |
| `references/` | методология и пороги каждого шага |
| `scripts/` | нормализация отчётов, доступ к Метрике, анализатор площадок, рендер PDF |
| `assets/` | словарь мусорных имён площадок + образец `findings.json` |
| `evals/` | тест-кейсы скилла |

## Что делает — 7 шагов

0. Скоуп аудита (логин, период, KPI, счётчик/цели)
1. Инвентаризация и структурный аудит
2. Статистика по кампаниям (+ атрибуционный кросс-чек Метрики)
3. ⭐ Майнинг поисковых запросов: минусация + действия по фразам (ядро бывшего phrase-minus) — **субагент** `/search-queries`
4. ⭐ Чистка площадок РСЯ (ядро бывшего rsya-minus) — **субагент** `/rsya-placements`
5. ⭐ Корректировки ставок (точки роста) — **субагент** `/bid-segments`
6. Объявления и релевантность
7. Сборка финального PDF-отчёта (дашборд)

## Архитектура: оркестратор + субагенты

Оркестратор держит общую картину в основном контексте (скоуп, `_state.json`, гейты, сборка отчёта). Три тяжёлых шага сбора данных (поисковые запросы — Шаг 3, площадки РСЯ — Шаг 4, сегменты ставок — Шаг 5) вынесены в изолированные субагенты (`context: fork`): они собирают гигантские TSV-отчёты в своём контексте и возвращают наверх **только сводку ≤20 строк**. Это не даёт контексту оркестратора распухнуть к моменту сборки отчёта. **Если форк недоступен** — шаги выполняются инлайн по тем же reference/scripts. Делегирование — оптимизация, а не жёсткая зависимость.

Все субагенты помечены `disable-model-invocation: true` (сами не запускаются) и несут **read-only** набор тулов.

**Шаг 4 — это перенесённый внутрь аудита движок бывшего отдельного скилла `yandex-direct-rsya-minus`**: анализатор `analyze_placements.py` + словарь `placement_patterns.json` + ruleset `rsya-minus-rules.md`. Он отдаёт готовый к вставке `minus_list.txt` по кампаниям.

**Шаг 3 — это движок бывшего скилла `yandex-direct-phrase-minus`** (`search-query-miner`): `query_analyzer.py` + `run_analysis.py` + словарь `query_patterns.json` + ruleset `phrase-minus-rules.md`. За один прогон даёт минусацию запросов (минус-слова кампании + минус-фразы группы → `minus_keywords.txt`) и действия по ключевым фразам (ставки/статус → `03_phrase_actions.md`).

## Принципы

- **Только чтение.** Ни оркестратор, ни субагенты не вызывают пишущие тулы. Решение и заливку правок делает маркетолог.
- **Деньги — с НДС, в рублях.** `IncludeVAT: YES` единая политика, чтобы расход по площадкам/сегментам сходился с расходом по кампаниям.
- **Доказательство обязательно.** Каждый флаг = числа + период + объём + порог. Мало данных — «недостаточно данных», а не выдуманный вывод.
- **Direct + Метрика вместе.** Самые сильные находки — там, где расход из Директа лёг на поведение из Метрики.

## Зависимости (для scripts)

Только стандартная библиотека Python 3. `render_report.py` печатает PDF уже установленным Chrome/Edge (без pip-пакетов); браузер не найден → сохраняет `.html` для ручной печати. Токен Метрики — `YANDEX_METRIKA_TOKEN` (или `YANDEX_DIRECT_TOKEN` со скоупом `metrika:read`) в окружении или `.env` в корне проекта.
